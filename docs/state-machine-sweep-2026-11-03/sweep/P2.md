## P2-1 · The two-sided trade window's one client slot (trade2) against the server's session machine
- Area: wire (both)
- Verdict: needs-thought
- Why: the client keeps ONE `trade2` slot for what the server holds as several records (outbound invite, inbound invites, a live session), its terminal messages carry no subject, and nothing clears the slot on a reconnect, so the window can be wiped while its session lives on, or survive a session that is gone.

- Concerns:
  - [stuck] (high) After a deploy, or a drop whose close the worker sees before the rejoin, the open/review window survives as a phantom. The server cancels the session in webSocketClose while the dropping socket can no longer hear it (index.js:6436, trade2.js:113-121; a rejoin that EVICTS a still-registered socket skips webSocketClose, join.js:759-772, and that session survives, so only that road is safe), a deploy simply forgets it (trade2.js:12 "in-memory, deploy voids it"), and the client never clears `trade2` on state_sync (wsClient.js:1647 clears ONLY the party, for exactly this reason: "rosters are worker-memory only, so a deploy ... may have wiped ours"). On the phantom, ✕, Cancel and Leave Trade all send trade2_cancel and wait (TradeWindowPanel.jsx:1243-1246, 1877); the server finds no session and answers nothing (trade2.js:419-426). The player cannot close it until a reload, and `tradeBagBus` stays attached (TradeWindowPanel.jsx:860-865), so every bag tap stages into the dead trade instead of opening the item's card (tradeBagBus.js:73-77); and the window's modal guard stays pushed (TradeWindowPanel.jsx:626, modalGuardBus.js guardPush), so the phone's chat composer will not open and the world chat feed stays hidden (ChatBubble.jsx:274, WorldChatFeed.jsx:403) for the rest of the session. Evidence: as cited. Docs: docs/specs/trading.md:152 says a deploy voids sessions "harmlessly" (true of the goods, not the window); no TRAPS entry.
  - [stuck] (medium-high) 'busy' is sent when EITHER side already has a session, and the opener's phone reads it as the end of whatever its slot holds. Tapping "Open trade" twice before the 'open' echo lands (the stub has no pending state, TradeWindowPanel.jsx:1091-1094), or tapping the partner (or anyone) in the world mid-trade and pressing Trade on their card (InspectPlayerPanel.jsx:257-268, no check of the current trade2), sends a second trade2_open → 'busy' (trade2.js:136-138) → setTrade2(null) with "They are already trading" (gameEvents.js:5022-5026). The session stays live server-side; the player has no window to cancel it, every new open answers 'busy', and the session's idle clock is refreshed by the partner's every edit (trade2.js:193), so it can outlive the 5 min TTL. Exit: the partner cancels, or a reconnect. Docs: trade2.test.mjs:101 tests 'busy' for a third party only.
  - [race] (medium) A trade2_invite that lands inside the ≤1.5 s done-watch is overwritten: trade2_invite sets the stub but does not clear `S._t2DoneWatch` (gameEvents.js:4916; only trade2_state does, 4931-4934), so the watcher then sets the receipt over it (4996) and the receipt's timer nulls it (TradeWindowPanel.jsx:769). The inviter waits 60 s for an 'expired'. Docs: none found.
  - [divergence] (medium) The server's invite-end messages carry no subject (`{state:'cancelled', reason:'expired'|'declined'|'disconnected'}`, trade2.js:415, 451), and the client clears its one slot on any of them (gameEvents.js:5022). B with A's ignored invite who has since opened toward C ('invited') loses the waiting drawer when A's invite expires, though B>C is still live; a stale 'expired' inside the done-watch kills the receipt before it shows (4931-4934). The reverse also holds: declining one stub clears EVERY invite key B is part of, telling peers B never saw (trade2.js:403-417). Docs: trade2.js:398-402 guards only the OPEN-session case.
  - [divergence] (low) The accept cooldown is drawn from the server's `changedAt` against the phone's clock (TradeWindowPanel.jsx:1154); a phone ahead of the worker shows Accept early and the server answers `reason:'cooling'` (trade2.js:226-227), which nothing renders (no client reads 'cooling'), so the tap silently does nothing. A server-clock offset exists elsewhere (src/ui/mobile/farmBus.js:55) but is not used here. Docs: TradeWindowPanel.jsx:1150-1153 calls the mirror display-only.
  - [combo] (low) Back (trade2_ready false) clears only that side's ready and leaves the other's `confirmed` true (trade2.js:209), so "accepted while not ready" is reachable; re-readying without an edit returns to a review already half-accepted. Not a scam route (every edit resets confirms), but the "both must accept again" reading of v2.3.1754 does not hold after a Back.
  - [persistence] (low) The commit's items, gold and pets go out in ONE write (trade2.js:323-331, inbox.js:274-297), but each escrowed weapon is delivered AFTER it, one awaited credit and delete at a time (trade2.js:356-367). A restart (every worker deploy) between the two leaves a `trade2wpn:` record with no `wpndeliver` stamp and no live session, and the join-path sweep REFUNDS it to the giver (trade2.js:650-668): the giver keeps the weapon and is paid for it. v2.3.3294 closed this for the other lanes only; server/test/trade2.test.mjs:319-334 sweeps hand-built records but never restarts mid-commit. Docs: trade2.js:323-328.
  - [combo] (low) Nothing cancels a session on death or a zone change (no caller of `_t2Cancel` outside trade2.js; grep), so a dead or dungeon-bound player keeps an open window; the commit's validation catches lost goods.
- Making it explicit: one client reducer keyed by subject (`{inviteIn:{from}, inviteOut:{to}, session:{id,stage}}`) fed by messages that name their subject (add `from`/`target`/`id` to every 'cancelled'), cleared on state_sync like the party, with 'busy' split into "you are already trading" (re-send the live snapshot) vs "they are".

  - [divergence] (low) `stage` is never re-synced from the server mid-session (deps are only the session id, TradeWindowPanel.jsx:722-732, deliberately), but the server's sanitizer keeps at most 20 item keys and drops the rest silently (trade.js:86). The review screen catches it; the live lane lies. Docs: the v2.3.1235 note (729-731) chose not to resync to keep the cursor still.

Since v2.3.1754 an edit at the offer stage resets READY (trade2.js:190) and a confirm can only exist on the review screen, where both bags are released. So the common last-second swap (you readied, they change an item) shows no notice: your "Ready ✓ — waiting" just turns back into "Ready to trade". The v2.3.2293 note relies on that notice to announce the event (1484-1486). The review screen still shows the true offer, so this is a lost warning, not a scam route. Docs: TradeWindowPanel.jsx:734-742.
  - [combo] (low) `leaveAsk` is reset only by a new session id (727), so a "Leave this trade?" strip opened at the offer stage follows the pair onto the review screen (1432) after both ready.
  - [opacity] (low) The 200 ms `nowTick` interval re-renders the whole window five times a second for its entire life (710-713), including the 60 s invite stub and the 'invited' wait, where nothing counts down. Bounded by the mount, so not a leak.
- Making it explicit: derive the notice from `changedAt`/`changedBy` (already on the wire, trade2.js:86) instead of confirm-flag edges, and reset `leaveAsk`/`goldAck` from one `stageKey = id + stage + changedAt`.
