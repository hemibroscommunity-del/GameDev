# S2 — server join, identity and logins, saves and migrations, test mode, live flags, admin and dev levers

## S2-1 · The join's admission pipeline (one socket's life from upgrade to "joined")
- Area: server
- Verdict: needs-thought
- Why: the "one join a socket" guard and the room's bookkeeping both key on `session.id`, which is set only after an await that can open the input gate, so a close or a second join in that gap is unhandled (latent until the account check is switched on).
- Key files: server/src/join.js:624-774, server/src/index.js:5134-5161, server/src/index.js:6357-6458, server/src/verify.js:67-94, server/src/botsig.js:481-496
- Entity: one WebSocket's session (`this.sessions` entry) and the player state it creates
- State lives in: `session.id` (join.js:774; null until then), membership in `this.sessions` (index.js:4935 set at the upgrade; deleted at join.js:652,691,700,710,716,728,744,940, verify.js:93, index.js:6448), `this.playerState[id]` (join.js:876; deleted at join.js:927), `session.data/char/protocolVersion/pres2/nearJoin/wheelNear/revealBag/_mapWatchUntil/_looks/_wheelWhole/lastPlayerStateSent` (join.js:812-862), `_keyOut` (join.js:669)
- States: upgraded-not-joined, authing (awaiting `_verifyJoinAuth`), refused (auth / key / locked / device / verify / frozen / linger_wait / magic id), admitted-pre-state (session.id set, playerState being built), rpg-read-failed (closed 1011), joined (state_sync sent), superseded (evicted by a later join of the same id), closed
- Transitions:
  - socket upgrade: none → upgraded-not-joined (index.js:4927-4935, flags + hidden warmed first index.js:4911-4914)
  - first `join`: upgraded → authing (index.js:5141 guard `if (session.id)`, join.js:674)
  - auth answer 'verify'/'key'/'locked'/'device'/false/frozen: authing → refused, socket closed 4014/4017/4018/4016/4003/4004 and deleted from sessions (join.js:679-730)
  - lingering body elsewhere: authing → refused `linger_wait` (join.js:739-746)
  - a live session with the same id: that session → superseded, deleted and closed 1000 WITHOUT webSocketClose, only `_botfpFlush` (join.js:758-772)
  - `session.id = msg.id`: authing → admitted-pre-state (join.js:774), playerState rebuilt fresh (join.js:876)
  - `_loadRpg` throws (read failed, or a newer worker's save): admitted → closed 1011, place remembered, playerState deleted, webSocketClose run (join.js:919-942)
  - state_sync + player_state sent: admitted → joined (join.js:1726, 1853); `_keysAfterJoin` last (join.js:1909)
  - `_handleJoin` throws anywhere: → socket closed 4010, nothing else undone (index.js:5156-5161)
  - socket close: any → closed (index.js:6357; does nothing for a session with no id but delete it, index.js:6362, 6448)
- Guards that read it: one-join-a-socket (index.js:5141), every handler's `session.id` check, `getPlayerCount` / `getAllPlayerData` iterate `this.sessions` (index.js:6598-6616), but the roster, monster AI, `_activeZones` and respawn iterate `this.playerState` (tick.js:671, index.js:1888, 1940, 3513)
- Counterpart/linked: client wsClient.js join_rejected / onclose switch (`_vfPending`, `_dvPending`, `_kyPending`, `_lkPending`, `_rfPending`, `_joinRejectedFatal`, wsClient.js:345-385, 1411-1506, 4487-4631); S2-2 respawn replay; S2-3 auth lockout; S2-6 device lock; S2-7 login keys; S2-8 account check; flood.js join window (`_floodNoJoin`, tick.js:165)
- Concerns:
  - [guard-drift] (high confidence) A second login is a free escape from a fight, the one the linger (v2.3.3260) was built to close. The linger is decided only in webSocketClose (`_lingerOnClose`, index.js:6370; linger.js:68-97), and `_lingerOnJoin` refuses a join only while a body is ALREADY lingering (linger.js:159-166). The eviction of a live session with the same id skips webSocketClose (join.js:758-772), so nothing asks whether that player was in a fight. Two tabs share one identity by design (CLAUDE.md §5; identity.md:89): a player losing a No man's land fight opens the game in a second tab, which starts in today's town (lastplace.js:31-35); its join evicts the fighting tab, is not judged (a join out of the Wheel is taken as named, lastplace.js:186-203), and puts them in town at once with their bag and their HP as last SAVED (S2-13: up to 10 s of PvP damage undone, combat.js:2576). No modified client needed. Evidence: join.js:739-774, index.js:6370, linger.js:159-166. Docs: TRAPS §162 (every way a session ends does the close's duties); pvp-fights.md §6 says a fresh launch "waits until the body has gone"; linger.test has no second-login case.
  - [race] (medium confidence) A close during the account check's fetch leaves a ghost body. `_verifyJoinAuth` → `opts.needVerify()` → `_verifyToken` → `fetch` (verify.js:78, up to 6 s) opens the input gate (handoff rule 9). If the socket closes then, webSocketClose finds `session.id` unset, skips the leaving and deletes the session (index.js:6362, 6448). The join then resumes, sets `session.id`, builds `this.playerState[id]` (join.js:876) and broadcasts `player_join` (join.js:1652-1653); `ws.send(state_sync)` (join.js:1726, not in a try) may throw on the closed socket, and then the router only closes it again with 4010 (index.js:5160) and undoes nothing; if it does not throw, the join simply completes for a socket that is gone. The state has no session, so no close will ever remove it, the AFK sweep walks only `this.sessions` (tick.js:162), and the presence roster keeps sending it to every phone (tick.js:671). The body stays until a deploy or a join of that id. Latent: only for a character with no `auth:` record while TURNSTILE_SITEKEY is set (empty today, server/wrangler.toml:61), or a flagged player with `botsig_reverify` on (botsig.js:489). The same gap covers `_sigReverifyOk`'s fetch at join.js:683. Evidence: join.js:517, 674-683, 774, 876; verify.js:78. Docs: handoff rule 9; TRAPS §162 (every way a session ends must do the close's duties); no note on a close mid-verify found (verify.test has none).
  - [race] (medium confidence) The same gap reopens v2.3.3274's ONE JOIN A SOCKET. The guard reads `session.id` (index.js:5141), which is still null while join #1 awaits the fetch, so a modified client's second `join` (another id it holds the key for) runs to completion. Join #1 then overwrites `session.id`, and the second id's player state is left with no session, the exact "left the first player in the room for good" case the guard was written for. Evidence: index.js:5135-5144, join.js:774. Docs: the v2.3.3274 comment itself.
  - [persistence] (medium confidence) The eviction skips the close's duties except the bot summary (join.js:768). The old state's unsaved pools and paced saves (`ps._regenDirty`, set by `_saveRpgPaced` flood.js:284-289 and `_saveRpgPools` persistence.js:186-194) are dropped when the join rebuilds the state from storage (join.js:876, 921). A reconnect within 10 s of a paced equip past the burst, or of a coalesced hit, comes back at the stored value. Losing regen is the documented trade (handoff rule 4); a hit and a paced equip are not regen. Docs: TRAPS §162 ("every way a session ends does the close's duties ... or the reconnect path must merge"); handoff rule 4 and 27.
- Making it explicit: a `session.phase` ('open' | 'authing' | 'admitted' | 'joined' | 'gone') set at each step, with the one-join guard reading `phase !== 'open'` and the join checking `this.sessions.has(ws)` after every non-storage await (as `_keysAfterJoinNow` already does, loginkeys.js:117, 159).

## S2-2 · The owed respawn replayed at a rejoin
- Area: wire (both)
- Verdict: needs-thought
- Why: the join reads `_respawnOwed` from the player state it has just rebuilt from scratch, so the replay of an undelivered `player_respawned` can never fire.
- Key files: server/src/join.js:1876-1885, server/src/join.js:876-881, server/src/index.js:3596-3607, src/ui/BroTown.jsx:4992-5014
- Entity: a player who died and respawned while their socket could not hear it
- State lives in: `ps._respawnOwed` (index.js:3596, 3606; deleted at join.js:1878)
- States: not owed, owed (respawn happened server-side, the phone never told), replayed
- Transitions:
  - respawn with no socket, or a send that threw: not owed → owed (index.js:3596, 3606)
  - rejoin: owed → replayed, `player_respawned {zone}` sent after state_sync (join.js:1877-1885) — intended
  - the old state object dropped: webSocketClose deletes it (index.js:6397), `_lingerEnd` deletes it (linger.js:134), or the join replaces it (join.js:876)
- Guards that read it: join.js:1877 only
- Counterpart/linked: client death state `S._dying`, cleared only by `player_respawned` (wsClient.js:3242 `applyLocalRespawn`) or the 20 s stuck-dead watchdog (BroTown.jsx:5010-5013); S2-1 (the join rebuild); linger.js
- Concerns:
  - [stuck] (high confidence) Dead code. `this.playerState[msg.id]` is a NEW object built from defaults and the allowlisted `cleanJoinData` (join.js:876-881), which can never carry `_respawnOwed`. Every path that leaves the flag on the old object also drops that object before line 1876 reads the new one: the close (index.js:6397), the linger's end (linger.js:134), the rebuild itself (join.js:876). So a player who died in a backgrounded tab comes back frozen on the death spot until the client's own watchdog stands them up after 20 s with hp > 0 (BroTown.jsx:5010). The comment on the watchdog says the worker replay is the real fix (BroTown.jsx:4999-5001). Evidence: join.js:876, 1876; index.js:3596. Tests: combat-lifecycle.test.mjs:1203-1237 checks only that the flag is SET; nothing tests the replay. Docs: v2.3.1822 comments only.
- Making it explicit: carry the debt across the rebuild (read `_respawnOwed` off the old state with `_livePlace` at join.js:875, or keep it in a Map keyed by id beside `_lastPlaces`), and add the join half to the suite.

## S2-3 · The per-character wrong-key lockout (shared by the join and the login door)
- Area: server
- Verdict: watch
- Why: a small time-gated counter, but its two writers count different things and the count never decays.
- Key files: server/src/join.js:486-565, server/src/account.js:155-191
- Entity: one player id's failed key attempts
- State lives in: `this._authFails` Map id → `{count, until}` (join.js:488, 561-564; account.js:156, 187-190; deleted join.js:535, 543, account.js:173)
- States: clean (no entry), counting (count 1-4), locked (until > now), lock-expired (count 0, until past)
- Transitions:
  - wrong old key, a refused new key, a retired old key at a join: count += 1; at 5 → locked for 60 s, count 0 (join.js:536, 541, 552, 560-565)
  - wrong old key at the login door: the same, by its own copy (account.js:187-190)
  - right old key or right new key: → clean (join.js:535, 543; account.js:173)
  - time: locked → lock-expired when now > until (read join.js:500, account.js:158)
- Guards that read it: join.js:500 (`rec.until > now && !_nkLock` → 'locked'), account.js:158
- Counterpart/linked: client `_lkPending` / close 4018 waits and retries (wsClient.js:379, 4564); S2-7 login keys (a new key skips the lock at join.js:500)
- Concerns:
  - [guard-drift] (high confidence) Two copies of the counter (join.js:560-565, account.js:187-190) and they disagree on what counts: a retired old key (`auth.oldGone`) counts a failure at the join (join.js:541) but answers 'keychanged' without counting at the door (account.js:171); a new-shaped key that is not the character's counts at the join (join.js:536) but at the door is just `exists:false` with no id (account.js:146-149). The module header says the door "is never a weaker oracle than the join gate" (account.js:16-20) and keeps "one shared budget" (account.js:91-95). Low impact today. Docs: account.js header; none in TRAPS.
  - [stuck] (low confidence) The count has no window: four mistyped keys spread over days, then a fifth, lock the id for a minute; entries are only ever removed by a right key, so the Map holds one entry per registered id ever mistyped until a deploy. Evidence: join.js:561-564. Docs: none found.
- Making it explicit: one `_authFailCount` used by both files (account.js could call the join's), with a decay window like `_acctIp`'s.

## S2-6 · A character's devices: the device lock on `auth:<id>`, and its one-time fill
- Area: server
- Verdict: needs-thought
- Why: the lock's phase (open-first, known devices, owner's pass, sealed) is spread over four optional fields of the login record, written from the join, the login door and three owner tools, and its kill switch is not read the same way by every reader.
- Key files: server/src/devicelock.js:140-160, server/src/devicelock.js:165-252, server/src/devicelock.js:278-328, server/src/join.js:519-524, server/src/account.js:174-181
- Entity: one character's login record, and the room's one-time fill
- State lives in: `auth.devs` [{d, at}] (join.js:523; devicelock.js:154-159, 215, 290), `auth.pass` {until, at} (devicelock.js:286; deleted 158, 292), `auth.sealed` (devicelock.js:291; deleted 158), `devlock:filled` (devicelock.js:220), memory `_devFilled`, `_devFillP`, `_devFillFailAt`, `_devFillInfo` (devicelock.js:166-173, 221-222), counters `_dlCount` (devicelock.js:133)
- States: unlisted (no `devs`: registered before the lock, or with it switched off), open-first (`devs: []`, not sealed), known (devs listed), pass-open (pass.until > now), pass-stale (pass.until past, left on the record), sealed (devs [], sealed), sealed+pass; fill: not-run, running, failed (retry after 60 s), done
- Transitions:
  - a new character registers with the lock on: none → known ([device]) or open-first ([] when the join names no device) (join.js:522-524)
  - first decision for an unlisted record: the fill runs once (`_deviceFillReady`, devicelock.js:165-174) → known from `device:` / `botstat:` records (devicelock.js:178-223), or stays unlisted
  - a matching key from an unknown device on open-first/unlisted: → known, device appended (devicelock.js:144, 237, 152-160)
  - the owner's pass: → pass-open for 30 min (devicelock.js:286)
  - a new device under a pass: → known, pass deleted, seal broken (devicelock.js:158)
  - time: pass-open → pass-stale (devicelock.js:143 reads `until > now`)
  - the owner's Forget / Give a new key: → sealed, devs [], pass deleted, keys [], the live session put out (devicelock.js:289-317)
  - past 12 devices: oldest-added dropped (devicelock.js:156)
- Guards that read it: `_deviceDecide` (devicelock.js:140-146) from the join (devicelock.js:227-239), the login door and the restart (devicelock.js:243-252, account.js:180-181, 106), and the key handout (loginkeys.js:144); kill switch `_deviceLockOn` (devicelock.js:126-129)
- Counterpart/linked: client device screen (`_dvPending`, close 4016, wsClient.js:366-372, 4505-4515; src/ui/DeviceScreen.js); S2-5, S2-7; S2-17 (the live flags not loaded on the login door)
- Concerns:
  - [divergence] (medium confidence) The login door and the character list's restart read the kill switch from `this._liveFlags`, which only the socket upgrade warms (index.js:4911) and which `/api/account/*` is routed before (index.js:4875-4877). On a worker with no socket since it woke (an empty room after a deploy or an idle eviction), `_deviceLockOn()` reads null flags as ON (devicelock.js:127-128), so with `devicelock: false` thrown the door still answers `device: 'unknown'` and the restart still refuses 'device' (account.js:106, 180-181), while a join would be let in. A player typing their key on a new phone is told the character cannot be played there, the very lock the switch was thrown to lift. Evidence: index.js:4875-4877, 4911; devicelock.js:126-129, 243-252; device-lock.test.mjs:66-69 pre-sets `_liveFlags`, so the cold path is never run. Docs: device-lock.md "The switch" says the login check is put back as it was.
  - [leak] (low confidence) `_deviceFill` lists `device:` and `botstat:` whole, with no limit, from inside the first join that needs it (devicelock.js:190, 196, 231) — the rule-9 shape ("a single list() with no limit over a prefix that grows without bound is a bug on any hot path"). Once it has run it is marked and never runs again, so the risk is a failed fill: each retry, every 60 s, repeats the whole scan on a join (devicelock.js:167-171). Docs: handoff rule 9 second edge; device-lock.md "the one-time fill".
  - [stuck] (low confidence) A device used every day is never refreshed (`known` writes nothing, devicelock.js:237, by design for cost-guard), so a character played on a 13th device drops the OLDEST-ADDED one even if that is the player's own phone (devicelock.js:156); that phone is then refused until the owner's pass. Docs: device-lock.md says "the oldest added dropped past 12" — the trade is written down, its effect on a daily device is not.
- Making it explicit: one `lockPhase(auth, now)` returning 'unlisted' | 'open' | 'known' | 'pass' | 'sealed' beside `_deviceDecide`, and `_accountFetch` awaiting `_liveFlagsEnsure()` first, as `fetch` does for sockets.
