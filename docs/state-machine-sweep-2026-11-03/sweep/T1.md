# T1 · the world studio (public/tools/world): implicit state machines

Slice context: `public/tools/world/` is two things. (1) The **World Builder page** (`app.js`, `store.js`, `index.html`): its square-by-square ChatGPT painting loop is SUPERSEDED since v2.3.2935 ("squares are no longer painted one picture each. This page stays the plan, the blueprint ... and the home of the style key", docs/WORLD-MAP-PIPELINE.md:19-23), so that loop is a dormant owner tool; the style key it keeps is LIVE (the Ground and Object Studios read it). (2) **`core/ground-worker.js`**, the LIVE game's Wheel ground worker (started by src/game/wheelTrial.js:282-324 for every player), plus the pure generators it runs (layout, ground, placing, worldblocks, plan...). The pure algorithms (fuse, maxflow, image, png8, zip, rng, grid, wheel, wheelmap, prompt, footsteps, piecePalette, rises, placedfile, the plan's builders) hold no lifecycle and are not machines; their memos (layout.js FEATS/stands/lattice, ground.js PLANKS, rises.js LAYOUTS, plan.js `_standard`) are capped or WeakMap caches only.

- Area: tools
- Verdict: watch
- Why: each save is several separate IndexedDB writes with the project record last, so an error, a quota refusal or a reloaded tab mid-way leaves fused pixels the record does not know (or a record whose picture is gone); the loop is dormant.
- Key files: public/tools/world/app.js:596-617, public/tools/world/app.js:659-703, public/tools/world/app.js:732-765, public/tools/world/store.js:33-41, public/tools/world/app.js:878-905

  - Re-fuse everything: rebuild (app.js:853-857)
  - Restore: `clearAll()` → new record in memory → put each raw → style key → rebuild → record saved at its end (app.js:743-760)
  - Backup: zip the raws + record; `lastBackupAt = now` (app.js:705-730)

- Counterpart/linked: T1-4 (the chunk cache), T1-7 (store.js: one transaction per op), T1-6 (plan keys, backup nag); docs/WORLD-MAP-PIPELINE.md (the loop, superseded)
- Concerns:
  - [persistence] (medium) `keep()` flushes the chunks before the record is saved, with no try/catch (app.js:599-614, 842): a quota error on `put('raw')` or `saveProject`, or a tab closed in between, leaves the square's fused pixels in `chunks` while the record says unpainted and `S.pending` stays set. No toast says the save failed. Healed only by Re-fuse everything. Evidence: app.js:601-613. Docs: none found.
  - [persistence] (medium) `redo()` deletes the raw (app.js:698) and `rebuild()` clears every chunk (app.js:660) long before the record is saved (app.js:683); a rebuild is "a moment per square" over EVERY square (app.js:854). The page's own comment says iPhone Safari reloads a background tab (app.js:433-434): reloaded mid-redo, the record still lists the square with no picture, `chunks` holds only the squares re-fused so far, and the stored thumbnail still shows the old world (saveArtThumb only at the end, app.js:682). Evidence: app.js:686-700. Docs: none found.
  - [stuck] (low) one stored picture that no longer decodes makes `prepareGen` throw (app.js:543, 52) and aborts the whole rebuild for every later square, for Redo, Restore and Re-fuse alike, with a message that does not name the square (app.js:673).
  - [persistence] (low) Restore wipes the browser first (`clearAll`, app.js:744) and saves the record only after the rebuild (app.js:760 → 683): any failure in between leaves an empty `meta` with the raws and partial chunks behind (the backup file itself is unharmed). The backup's `version: 1` is never read back (app.js:710, 736-737) and the project record has no shape number (fields such as `planKey` were added later and are handled ad hoc, app.js:900-905).
- Making it explicit: commit order "record last, pixels re-derivable": write the record with a `pending: true` square first, then pixels, then clear the flag, and on start re-fuse any square still pending; or one IndexedDB transaction over `meta`+`raw` per Keep.
