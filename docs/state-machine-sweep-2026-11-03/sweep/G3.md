# G3 — client world rules (zone transitions, Wheel trial, dungeons, No Man's Land, doors, pins, time, presence, tours)

## G3-1 · The per-zone loading gate at a hub's exit (`S._zoneLoading`)
- Area: client
- Verdict: watch
- Why: a polled promise holder with four writers and ~25 readers that freezes the player; well guarded by two failsafes, but its 15 s cap lets entry race the load it was waiting for.
- Key files: src/game/zoneTransitions.js:821-850, src/game/zoneTransitions.js:580-584, src/game/zoneTransitions.js:653-656, src/ui/BroTown.jsx:5479, src/game/wheelHome.js:128
- Entity: the local player's walk from a hub (town, the World View / Wheel) into a zone
- State lives in: `S._zoneLoading` = {toZone, from, done, t} (src/game/zoneTransitions.js:838); `done` flipped by the load promise (zoneTransitions.js:848)
- States: idle (null), loading (done:false, player frozen at the exit, overlay up), loaded (done:true, waiting for next frame), consumed (null; zone flipped), abandoned (null; no flip)
- Transitions:
  - player within TOWN_EXIT_R of an exit whose zone is not resident (or town scenery not ready): idle → loading (zoneTransitions.js:837-849)
  - preloadZoneAssets resolves OR the 15 s cap: loading → loaded (zoneTransitions.js:845-848)
  - next frame at the same exit: loaded → consumed, overlay hidden, previous zone's map + variants freed, entry body runs once (zoneTransitions.js:823-836)
  - no exit in reach / a different exit wins: loading|loaded → abandoned (zoneTransitions.js:653-656)
  - not in a hub any more (server-forced flip, respawn, dungeon) or older than 20 s: → abandoned (zoneTransitions.js:580-584)
- Guards that read it: movement freeze (src/ui/BroTown.jsx:5479, 5337), jump (src/game/jump.js:266), NPC talk (BroTown.jsx:6990, 7099), the Wheel trip (src/game/wheelHome.js:79, 128), the Wheel worker's keep-alive `coming` (src/game/worldTrial.js:513), town veil lift (zoneTransitions.js:303) and free timer (zoneTransitions.js:356, 360), farm hold lift (src/game/farmTrip.js:76), dev warp (zoneTransitions.js:507), level-band warning (zoneTransitions.js:767), many HUD/renderers (guideArrow.js:309, minimapRenderer.js:792, effectsRenderer.js:8172, targeting.js:598, ...)
- Counterpart/linked: server never sees the gate (currentZone is not flipped while loading, so the worker keeps the player in the hub: zoneTransitions.js:813-816). Linked: G3-2 (the shared overlay), G3-3 (the Wheel trip drives the player onto the stairs), G3-4 (the Wheel's `_ready` decides residency via tiledMaps.js:223).
- Concerns:
  - [race] (medium confidence) The cap resolves `done` at 15 s whether or not the load finished, and the load is never cancelled. For the Wheel, preloadWheel can outlast it (it waits up to 8 s for caps.wheelsize, up to 15 s for the renderer's word, then the plan build and the warm: worldTrial.js:391-441, wheelTrial.js:246,314); the player then walks in with `_ready` false and the ground popping in, and the orphaned preload later writes `_ready = true` regardless of what happened since (see G3-4). Evidence: zoneTransitions.js:845-848, worldTrial.js:442. Docs: the 15 s "self-heals on cache-miss" trade-off is stated for maps only (zoneTransitions.js:842-844); none found for the Wheel.
  - [stuck] (low) a hidden tab stops rAF, so the gate cannot be consumed; on return the 20 s age check abandons it and the next frame re-arms a second preload for the same zone (two preloadWheel runs in flight). Harmless today because wheelStart/wheelWarm dedupe (wheelTrial.js:283, 463), but nothing in the gate itself dedupes. Evidence: zoneTransitions.js:582, 837-849.
- Making it explicit: a small `zoneGate` object with `arm(toZone)`, `poll()`, `abandon(reason)`, a generation number the load's `.then` checks, and the readers asking `zoneGate.busy()`.

## G3-2 · The one loading veil and today's town's art hold (`_zoneLoadEl`, `S._townArtHold`, `S._wheelTripVeil`, `_townFreeTimer`)
- Area: client
- Verdict: needs-thought
- Why: one DOM veil is shown and hidden by at least five independent machines, each of whose hide checks a different subset of the others, so one owner can lift another's veil.
- Key files: src/game/zoneTransitions.js:214-253, src/game/zoneTransitions.js:295-364, src/networking/gameEvents.js:953-990, src/game/farmTrip.js:69-77
- Entity: the full-screen zone loading overlay, and today's town's NPC/building/map art
- State lives in: `_zoneLoadEl` (zoneTransitions.js:214), `S._townArtHold` {t, done} (zoneTransitions.js:333-334), `S._wheelTripVeil` (zoneTransitions.js:297, 310, 302), `_townFreeTimer` (zoneTransitions.js:281, 357), plus the other owners' flags `S._zoneLoading` (G3-1), `S._wheelDungeonOpening` (gameEvents.js:955), `S._farmArtHold` (farmTrip.js:69)
- States (town art): absent, held-for-the-Wheel (trip wanted: veil says "BroTown", nothing fetched), loading (veil "Town", player frozen), ready, free-pending (400 ms timer), freed
- Transitions:
  - in town, trip wanted, no veil: → held-for-the-Wheel, veil up (zoneTransitions.js:309-312); also pre-emptively from respawn / dungeon exit / farm exit via veilWheelTrip (zoneTransitions.js:295-299; respawn.js:99; wheelDungeons.js:292; zoneTransitions.js:1315)
  - in town, no trip, art missing: → loading, hold {t, done:false}, veil up, load raced against 15 s (zoneTransitions.js:332-345)
  - load settles: hold.done (zoneTransitions.js:344); next frame done or 20 s: → ready, veil lifted unless `_zoneLoading` (zoneTransitions.js:347-350, 300-304)
  - leave town: hold and trip veil lifted (zoneTransitions.js:353); art resident and not loading: → free-pending (zoneTransitions.js:354-357)
  - timer fires, still away and no gate heading to town: → freed (zoneTransitions.js:357-363)
  - other veil owners: hub gate show/hide (zoneTransitions.js:841, 583, 655, 825), Wheel dungeon opening show/hide (gameEvents.js:956, 978), farm hold show/hide (farmTrip.js:70, 76)
- Guards that read it: movement freeze on `_townArtHold` (src/ui/BroTown.jsx:5479), jump (src/game/jump.js:266), farm lift (farmTrip.js:76), the veil's own "intro clip up" self-heal (zoneTransitions.js:222-225)
- Counterpart/linked: G3-1 (hub gate), G3-3 (the Wheel trip decides `trip`), the dungeon opening in gameEvents.js (other slice), farmTrip.js (other slice); docs/specs/loading-gate.md
- Concerns:
  - [race] (medium) Hides disagree on who else may own the veil: `_liftTownVeil` checks only `_zoneLoading` (zoneTransitions.js:303); the hub gate's three hides check nothing (zoneTransitions.js:583, 655, 825); the dungeon opening's hide checks nothing (gameEvents.js:978); the farm hold checks `_zoneLoading`, `_townArtHold`, `_netHold` (farmTrip.js:76). Scenario: dungeon_started at a Wheel mouth puts up the veil for up to 8 s (gameEvents.js:973-976) and nothing freezes the player on `_wheelDungeonOpening` (BroTown.jsx:5479), so a land monster can kill them under it; the respawn (~5 s, server index.js:3501 respawnInMs) lands in today's town and calls veilWheelTrip (respawn.js:99); then the opening's `.then` runs `hideZoneLoadingOverlay()` (gameEvents.js:978) — the trip's veil is gone while `S._wheelTripVeil` stays true, so syncTownScenery never re-shows it (zoneTransitions.js:309) and today's town, none of its art fetched (zoneTransitions.js:326), is painted until the stairs' gate arms (wheelHome.js:151, ≥400 ms). Needs the opening's loads to outlast the death plus the ~5 s respawn (a slow phone or network). Evidence: as cited. Docs: v2.3.3025 "today's town never seen" (wheelHome.js:50-67); v2.3.3025 notes the same class of race for town-vs-gate only (zoneTransitions.js:283-290).
  - [combo] (medium) `S._wheelTripVeil === true` with `_zoneLoadEl === null` is reachable (above) and nothing reconciles the flag with the element; the flag is only ever reset by `_liftTownVeil` (zoneTransitions.js:300-304).
  - [opacity] (high) five owners, three flags and one element; the name on the veil is last-writer-wins (zoneTransitions.js:238-241), so the trip's "BroTown" can be overwritten by "Town" (zoneTransitions.js:335) when the trip lets go mid-veil.
- Making it explicit: a veil owner stack — `veil.hold(owner, name)` / `veil.release(owner)`, the element removed only when the stack is empty — with `_wheelTripVeil`, `_townArtHold`, `_farmArtHold`, `_wheelDungeonOpening` and the hub gate as owners.

## G3-3 · The trip down today's town's stairs into the Wheel's BroTown (`S._spawnToWheel`)
- Area: client
- Verdict: watch
- Why: a login/death/dungeon/farm "spawn" that is really an automated walk through a hub exit, its phase spread over four fields and a 30 s veil clock that lets go of the veil but never of the trip.
- Key files: src/game/wheelHome.js:43-158, src/game/zoneTransitions.js:684, src/game/respawn.js:99, src/game/wheelDungeons.js:291, src/game/zoneTransitions.js:1275
- Entity: the local player arriving in the world
- State lives in: `S._spawnToWheel` (wheelHome.js:45, 124, 126, 153), `S._spawnSince` (wheelHome.js:46, 124, 126, 150), `S._spawnAskedAt` (wheelHome.js:47, 146), `S._wheelSpawnInit` (wheelHome.js:119); reads `S._zoneLoading` (G3-1), `S._serverCaps`, `S._dying`
- States: not-yet-run, wanted-waiting-for-world (no player/channel/caps, or dying; clock held while no caps), settling (400 ms), on-the-stairs (placed every frame), gate-loading (hub gate armed), arrived (in the Wheel), cancelled (somewhere else / no door), veil-expired (TRIP_VEIL_MS passed, trip still wanted)
- Transitions:
  - first frame in town: not-yet-run → wanted (wheelHome.js:118-121)
  - death respawn into town / Wheel dungeon exit / farm gate out: → wanted (respawn.js:99; wheelDungeons.js:291; zoneTransitions.js:1275)
  - caps + channel + player and not dying: wanted → settling (wheelHome.js:150) → on-the-stairs after SPAWN_SETTLE_MS (wheelHome.js:151-157)
  - hub gate arms at the stairs (Mayor gate passed by wheelSpawnPass, zoneTransitions.js:684): → gate-loading (wheelHome.js:128)
  - in a World View zone: → arrived, flags cleared (wheelHome.js:124)
  - in any zone but town: → cancelled (wheelHome.js:126); no stairs exit: → cancelled (wheelHome.js:153)
  - 30 s since the clock (re)started: the veil lets go (wheelHome.js:70-73), the loading screen stops waiting (wheelHome.js:78), but `_spawnToWheel` stays true
- Guards that read it: wheelTripVeiled (wheelHome.js:70) → syncTownScenery's `trip` (zoneTransitions.js:307), tileRenderer's deferred town map (src/rendering/systems/tileRenderer.js:881); wheelArrived/waitForWheelArrival for the intro clip (wheelHome.js:75-95); the Mayor-gate bypass wheelSpawnPass (wheelHome.js:110); the minimap star cue (src/rendering/systems/wheelMinimap.js:1144); the static twin townSkippedOnTheWay (wheelHome.js:107; preloadAnimations.js:420, pixiRenderer.js:122)
- Counterpart/linked: the server respawns into 'town' and sees an ordinary walk down the stairs; G3-1, G3-2; the Wheel's commons gate (G3-7); docs/specs/wheel-arrival.md
- Concerns:
  - [stuck] (low) After the veil lets go (wheelHome.js:72) the trip has no TTL of its own: when the player/channel/caps/not-dying condition finally holds, a player who has meanwhile been shown today's town (its art loaded, unfrozen) is snatched onto the stairs (wheelHome.js:155-157) and taken into the Wheel. Latent: it needs the trip's preconditions (player, channel, not dying) to fail for 30 s after the caps came, which today is practically unreachable (a stuck `_dying` is cleared by the 20 s watchdog, BroTown.jsx:5011-5014), so it bites only if a new precondition is added there. Evidence: wheelHome.js:133-157. Docs: wheelHome.js:65-67 says only the veil is let go.
  - [race] (low) The veil's clock and the gate's clock are independent: once caps are in, a gate that is abandoned and re-armed (G3-1's 20 s failsafe after a hidden tab) can run past TRIP_VEIL_MS, `trip` turns false mid-load, and syncTownScenery starts loading today's town (35 MB NPCs + 11.3 MB map) under the Wheel's own gate and renames the veil "Town" (zoneTransitions.js:332-345). This is the v2.3.3729 waste the clock hold was added to stop. Evidence: wheelHome.js:68-73, zoneTransitions.js:580-584.
  - [authority] (low, by design) the "speak to Mayor Bro first" holds (town: zoneTransitions.js:684-710; Wheel commons: wheelHome.js:162-190) are client-only; harmless (the unarmed player only harms themselves).
- Making it explicit: `trip = { phase: 'wanted'|'settling'|'placing'|'loading'|'done'|'abandoned', since, veilUntil }` with one `tripTick`, and the veil and the trip expiring together.

## G3-4 · The Wheel's ground worker and the trial's "ready" flag (`_w`, `_initP`, `_info`, `_ready`, `_wheelAwayAt`)
- Area: client
- Verdict: needs-thought
- Why: the worker's life (start, wait for the renderer, ready, linger, stop) and the zone gate's residency flag `_ready` are written from three async places with no generation check, and a failed start is cached for as long as you stay in the Wheel.
- Key files: src/game/wheelTrial.js:282-324, src/game/wheelTrial.js:546-567, src/game/worldTrial.js:382-444, src/game/worldTrial.js:512-538, src/rendering/wheelGround.js:204
- Entity: the ground worker (plan, walk grid, objects, overview) and whether the Wheel counts as "resident" for the hub gate
- State lives in: `_w`, `_initP`, `_info`, `_grid`, `_pending`, `_warm`, `_filling`, `_here`/`_hereAsked` (src/game/wheelTrial.js:44-62), `_said`/`_sayWaiters` (wheelTrial.js:258-266); `_ready` (src/game/worldTrial.js:123, 442, 159, 535), `_wheelAwayAt` (worldTrial.js:119, 526-530); `noteWheelBuilt` (wheelSize.js:100)
- States: stopped, starting (worker made, waiting up to 15 s for the renderer's word), building (init posted), ready (`_info` set), failed (`_initP` rejected), warming (zone gate laying the first screen), lingering (left the Wheel, < 5 s), stopped again
- Transitions:
  - preloadWheel / wheelGround.update: stopped → starting (wheelTrial.js:282-289; wheelGround.js:204)
  - renderer said (or 15 s): starting → building, init posted with the size of the moment (wheelTrial.js:314-320)
  - 'ready': building → ready (wheelTrial.js:342-364); 'error' with no id or onerror: → failed (wheelTrial.js:291-297, 329)
  - preloadWheel finishes: `_ready = true` (worldTrial.js:442)
  - ground destroyed (not a renderer rebuild): `_ready = false` (wheelGround.js:489 → worldTrial.js:159)
  - out of the Wheel and not coming for WHEEL_LINGER_MS: → stopped, `_ready = false`, walk grid dropped (worldTrial.js:527-537 → wheelTrial.js:546-567)
- Guards that read it: the hub gate's residency (src/rendering/tiledMaps.js:223 `isZoneMapResident` → worldTrialReady), the walk grid handed to isSolid/nudgeSpawnToWalkable (worldTrial.js:520-523), `wheelRunning()` (worldTrial.js:527), every map/door/NPC lookup through `wheelInfo()`/`wheelObjectsInfo()`/`wheelMapInfo()` (wheelTownDoors.js:59, wheelDungeons.js:107, wheelNoticeboard.js:49)
- Counterpart/linked: public/tools/world/core/ground-worker.js (the worker itself); G3-1 (gate), G3-5 (size), wheelGround.js / wheelObjects.js (renderer, other slice); docs/specs/memory-in-the-wheel.md, docs/specs/wheel-in-blocks.md
- Concerns:
  - [race] (medium) `_ready = true` is written by whichever preloadWheel finishes, with no check that the trip it belonged to is still current. Scenario on a slow phone: the gate's 15 s cap lets the player in before preloadWheel ends (G3-1); they die; the tile renderer's rebuild destroys the ground and `_ready = false` (tileRenderer.js:435 → wheelGround.js:489 → worldTrial.js:159); the old preload then finishes and sets `_ready = true` (worldTrial.js:442) — the next trip down the stairs finds the Wheel "resident" (tiledMaps.js:223), arms no gate and walks in unwarmed under a veil that `_liftTownVeil` drops on arrival (zoneTransitions.js:353). If wheelStop ran in between (worldTrial.js:531), wheelWarm's chunks reject 'stopped' and resolve (wheelTrial.js:467-468), the preload runs on, and `_ready = true` stands with no worker at all. The objects' loader beside it already guards exactly this with a generation number (src/rendering/wheelObjects.js:320, 334, 343: `rec.gen !== _gen`); `_ready` has none. Evidence: worldTrial.js:439-443, wheelTrial.js:546-567. Docs: none found.
  - [stuck] (medium) A worker that fails to start (its module script or imports fail to load: `onerror`, wheelTrial.js:291-297) leaves `_initP` rejected and `_w` set; while you stay in the Wheel syncWheel never stops it (worldTrial.js:526), so every retry (wheelGround.js:204) gets the cached rejection: flat sea, no walk grid (worldTrial.js:520), no objects, no doors, no Mayor Bro (_spawnWheelNpcs returns null without the worker's objects: src/ui/BroTown.jsx:930-933, 4968) — for a new player, no way to get the first quest until a death or reload. A Worker constructor that throws never sets `_w`, so `_initP` stays rejected for the page's life. The reason shows only on the tester HUD (worldTrial.js:583). Evidence: wheelTrial.js:283-288. Docs: worldTrial.js:378-381 states "flat sea" as the intended fallback for a browser that cannot run workers, not for a transient load failure.
  - [leak] (low) wheelStop while the start waits for the renderer returns without settling `_initP` (wheelTrial.js:315), and a stop after 'init' was posted terminates a worker that will never answer: the awaiting preloadWheel and its closures hang for the page's life (only `_pending` is rejected, wheelTrial.js:560).
  - [stuck] (low) `_hereAsked` is cleared only by a 'where' answer or a stop (wheelTrial.js:367, 566): a worker that stops answering freezes `wheelHere`, whose `fresh` gates the land music's first word (src/game/wheelMusic.js:98).
- Making it explicit: one `wheelWorker` record `{gen, phase: 'stopped'|'starting'|'building'|'ready'|'failed', p}`; preloadWheel captures `gen` and writes `_ready` only if unchanged; a failed phase retries after a back-off instead of caching the rejection.
