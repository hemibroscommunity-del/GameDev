## S8-1 · Party invite handshake (invite, accept, decline, expire)
- Area: wire (both)
- Verdict: fine
- Why: a pending invite is one timestamp in a Map keyed `from>to`, checked at accept, refreshed on a re-invite and swept by the tick; the client card has its own matching clock.
- Key files: server/src/party.js:370-421, server/src/party.js:423-493, server/src/party.js:495-502, server/src/party.js:618-623, src/networking/gameEvents.js:5055-5090
- Entity: an (inviter, target) pair
- State lives in: `this._partyInvites` Map `'from>to' -> ts` (party.js:376, 415); client `party` slot `{invite:true, from, ts}` (gameEvents.js:5063)
- States: none, pending(ts), accepted, declined, expired
- Transitions:
  - party_invite (target online, not busy, not unknown, party not full, >= INVITE_REPEAT_MS since the last card): none/pending → pending(now) (party.js:413-420)
  - party_accept within INVITE_TTL: pending → accepted (deleted first, then membership) (party.js:428-429, 436-492)
  - party_accept after INVITE_TTL: pending → expired + `party_error expired` (party.js:437-439)
  - party_decline: pending → declined + notice to inviter (party.js:500-501)
  - tick: pending older than INVITE_TTL → deleted (party.js:619-622)
  - client card: shown on party_invited, cleared after PARTY_INVITE_TTL_MS with a {from, ts} identity check (gameEvents.js:5085-5089)
- Guards that read it: accept requires a recorded ts (party.js:427-436); re-invite spacing (party.js:413-414); target busy/unknown (party.js:386-388)
- Counterpart/linked: client mirror PARTY_INVITE_TTL_MS (gameEvents.js; spec party.md "Client mirror"); S8-2 membership
- Concerns:
  - [divergence] (low) The header and spec say the invite is "recorded per-sender-session" (party.js:15-16, docs/specs/party.md wire table), but the key is the stable player id pair, so an invite survives the inviter's reconnect. Harmless (the inviter is still the same player). Evidence: party.js:413-415. Docs: party.md says "rule 14 ... the inviter's own session".
- Making it explicit: not worth it.

## S8-2 · Party membership and the stored roster (memory + storage, unknown, load/heal, leave/kick/disband, restart)
- Area: server
- Verdict: needs-thought
- Why: one roster lives in four in-memory structures plus two storage keys, its meaning changes under three live switches, and a switch flip leaves states the code has no exit for.
- Key files: server/src/party.js:218-276, server/src/party.js:521-546, server/src/party.js:564-614, server/src/party.js:280-309, server/src/clanparty.js:108-178
- Entity: a party, and each player's membership in one
- State lives in: `this._parties` Map id→party (party.js:221, 477), `this._partyByPlayer` Map pid→party (party.js:222, 482), `this._partyUnknownIds` Set (party.js:223, 226, 237, 241), `p.members`/`p.meta`/`p.ts` (party.js:464-481), storage `party:<id>` (party.js:205) and `party_by_player:<pid>` (party.js:209-210); writers also clanparty.js:160-162, alliance.js:184/336 (via _partyStore), persistence.js:542 (_partyOnReset)
- States: partyless, member(online), member(offline, keep), unknown (read failed or newer shape), party in memory with nobody online, disbanded
- Transitions:
  - accept: partyless → member; a fresh party is created with the inviter (party.js:455-487)
  - join with no party in memory (partykeep on): partyless → member (record loaded, members healed against their own indexes) or → unknown on a throw/newer shape (party.js:218-276, 568-572)
  - leave / kick: member → partyless, terminal `party_state {state:'none'}`; one left → disbanded (party.js:504-546)
  - character restart: member → partyless, in memory or in storage (party.js:280-309; persistence.js:539-542)
  - clan conversion: clan member → member of a new stored party (clanparty.js:136-163)
  - tick (partykeep off): away past OFFLINE_GRACE_MS → removed 'offline' (party.js:627-632)
  - deploy: memory wiped; client clears on state_sync, join re-sends (wsClient.js:1641-1647; join.js:1889-1897)
- Guards that read it: invite (party.js:383-392), accept (party.js:446-462), kick leader-only (party.js:513), dungeon pull (dungeon.js:364), NML/PvP party checks (nomansland.js:299-300, index.js:3138-3139), presence (presence2.js:79), alliance everything (alliance.js:177, 209, 311, 382, 456)
- Counterpart/linked: client `party` slot and `S._party` (gameEvents.js:5091-5129, PartyHUD.jsx); S8-3 leader, S8-4 presence, S8-5 alliance, S8-9 clan conversion
- Concerns:
  - [stuck] (medium) Turning `partykeep` OFF with stored parties in memory: members who were offline when their party was loaded have no `awaySince` (party.js:255-259), and the old sweep needs one (party.js:629), so they are never removed; they show as `away` (reconnecting) forever and the party can hold up to 50 while the cap now reads 4 (party.js:171-173). The spec promises "an offline member removed after the grace" under the switch. Evidence: party.js:251-259, 627-632. Docs: docs/specs/party.md "Deploy order and the switch".
  - [stuck] (low) A player marked unknown (`_partyUnknownIds`) is cleared only by a later successful `_partyLoad`, which `_partyOnRejoin` runs only while partykeep is on and they have no party in memory (party.js:568). With the switch off, an unknown player can never invite or accept ('not-loaded', party.js:383-385, 450-452) until a deploy. The spec names the marker `session._partyUnknown` ("until it rejoins"); the code keys it by player id (divergence in the doc). Evidence: party.js:223-227, 383-386. Docs: party.md "A failed read fails closed".
  - [combo] (low) After a flip (or a crash between the index and record writes) a member can be listed by two parties; `_partyLoad` keeps the first live one (party.js:269-273), and `_handlePartyAccept` pushes without an `includes` check (party.js:480), so re-inviting such a player into the party that still lists them duplicates them in `members`, which `_allyCount` then counts twice (alliance.js:161-169). Evidence: party.js:269-273, 480.
  - [leak] (low) A party loaded at any member's join stays in `_parties`/`_partyByPlayer` for the worker's life with nobody online (party.js:634-636 skips it, nothing evicts it). Bounded by players who joined since the last deploy. Evidence: party.js:268-273, 634-636.
  - [opacity] (high) Writers in party.js, alliance.js, clanparty.js and persistence.js; three switches (`partykeep`, `alliance`, `clanparty`) change what a roster means; the index-is-truth healing rule is enforced only at load. Evidence: party.js:157-165, 245-250.
- Making it explicit: one `PartyStore` with a declared member state (`online|offline|away|unknown`) and the switch handled as an explicit migration (sweep or stamp `awaySince` on every offline member when partykeep goes off).

## S8-3 · Party leader succession (leave, restart, idle hand-on)
- Area: server
- Verdict: needs-thought
- Why: the idle-leader rule only fires for a leader with a `seen` stamp, and every former clan member who was offline at the conversion has none, so a converted clan's absent leader keeps the party forever.
- Key files: server/src/party.js:588-596, server/src/clanparty.js:145, server/src/clanparty.js:158, server/src/party.js:542, server/test/party-keep.test.mjs:258-277
- Entity: a party's `leader`
- State lives in: `p.leader` (party.js:466, 267, 542, 594; clanparty.js:145), `p.meta[leader].seen` (party.js:476, 481, 556, 586; clanparty.js:158)
- States: leader online, leader offline (< 7 d), leader idle (>= 7 d, hand-on due), leader unknown-idle (`seen` 0: never handed on)
- Transitions:
  - the leader leaves, restarts their character, or (partykeep off) is swept offline: leader → `members[0]`, online or not (party.js:542, 282, 630)
  - stored leader not in members at load: → `members[0]` (party.js:267)
  - a member's join, leader offline and `now - seen > LEADER_IDLE_MS`: → the first member online (party.js:590-596)
  - clan conversion: the clan's leader if free, else `free[0]` (clanparty.js:145)
- Guards that read it: kick (party.js:513), alliance name/war (alliance.js:313, 332, 384, 422), dungeon_start pull (dungeon.js `_dungeonPullPartyMembers`)
- Counterpart/linked: S8-9 (clan conversion writes `seen: 0`), S8-5 alliance (a leader is needed to name or declare war)
- Concerns:
  - [stuck] (medium-high) `_partyOnRejoin` hands on only when `+lm.seen > 0` (party.js:592). `_clanToParty` writes `seen: ps ? now : 0` (clanparty.js:158), so a clan leader who was offline at the conversion (the conversion runs at the FIRST join after the deploy, so almost always) has `seen` 0, and if they never come back the party never gets a leader who can kick, rename or declare war. The same holds when leadership passes on a leave to `members[0]` (party.js:542) and that member is a never-returning former clan member. The suite's idle-leader case only covers `seen > 0` (party-keep.test.mjs:258-277). Evidence: party.js:588-596, clanparty.js:145, 158. Docs: alliance.md step 3 says the rest count "from their next join (`seen` 0 ...)" -- written for the alliance count, not the leader rule; none found for the leader.
  - [stuck] (low) A leader who leaves hands the party to the oldest member even when offline (party.js:542); the online members then wait up to 7 days for the lazy hand-on. Documented ("Leaving passes it to the member who has been in longest"). Docs: party.md "The leader".
- Making it explicit: treat `seen` 0 as "never seen since a stored stamp" (use `meta.at` or the party's conversion time as the idle clock), and prefer an online member on a leave.

Evidence: alliance.js:250-275. Docs: ARCHITECTURE-HANDOFF rule 9 "second edge".
- Making it explicit: one `allyStatus(p, now)` used by the board and the tag, applying DROP for any party nobody is on.
