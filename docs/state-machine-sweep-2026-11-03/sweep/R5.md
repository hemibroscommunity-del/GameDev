## R5-1 · The renderer's own life: made (async), live, destroyed, rebuilt
- Area: rendering
- Verdict: needs-thought
- Why: initPixiRenderer is a long async birth (QA delay, up to 8 s of picture restores, app.init) whose result is assigned by a caller that never checks it is still wanted, while a dozen module-level "current renderer" handles are set on birth and never cleared on death.
- Key files: src/rendering/pixiRenderer.js:311-315, src/rendering/pixiApp.js:704-753, src/ui/BroTown.jsx:4001-4008, src/ui/BroTown.jsx:8401-8421, src/rendering/picsOnce.js:209-216
- Entity: the one Pixi renderer of the page (its Application, its systems, the canvas it draws on)
- State lives in: `pixiRef.current` / `window._pixiRenderer` / `window.__pixiActive` (src/ui/BroTown.jsx:4002-4008, 8414-8420), `_appRef` (src/rendering/pixiRenderer.js:207, 315), the module handles set at birth: `registerPrewarmRenderer` (pixiRenderer.js:324, entityRenderer.js:4300-4301), `deathCrumble.setRenderer` (pixiRenderer.js:345), `setFighterEffects` (:357), `setMonsterDeathRenderer` (:358), `setArrowWoundRenderer` (:359), `setWheelWaterRenderer` (:360), `setPaletteRenderer` (:364), `wheelRendererSaid` latch `_said` (:368, src/game/wheelTrial.js:260-266), `setOneBatchRenderer` (:372); canvas epoch `glEpoch` keying the <canvas> (BroTown.jsx:12770-12773)
- States: not-made, making (awaiting qaDelay -> restoreAllPictures (<=8 s) -> app.init), live, render-poisoned (see R5-4), destroyed, superseded (a newer epoch's canvas exists)
- Transitions:
  - effect run with no renderer: not-made -> making (BroTown.jsx:4001-4002 -> pixiRenderer.js:311-315 -> pixiApp.js:704-729)
  - init resolves: making -> live; pixiRef.current/_pixiRenderer/__pixiActive=true set unconditionally (BroTown.jsx:4002-4008)
  - init rejects: making -> not-made, retry by glEpoch bump with backoff <= 8 tries (BroTown.jsx:4103-4126)
  - no stencil / canvas fallback: live -> destroyed+remade via glEpoch (BroTown.jsx:4020-4058)
  - _rebuildRenderer / backToMenu (bootPhase) / dep change: live -> destroyed (effect cleanup: BroTown.jsx:8401-8421 -> pixiRenderer.js:924-964), then a new effect run -> making on a NEW canvas
  - destroy(): systems destroyed, render-target listeners cut, app.destroy (pixiRenderer.js:924-964) -- the module handles above are NOT reset
- Guards that read it: renderFrame calls update only while pixiRef.current (src/game/renderFrame.js:44-46); wsClient resume treats `__pixiActive === false` as "renderer dead" (src/networking/wsClient.js:5071-5073); the 5 s rebuild debounce (BroTown.jsx:4145-4170); the post-rebuild probe's "superseded" check `canvasRef.current !== canvas` (BroTown.jsx:4073) -- the only supersession check, and it is not on the assignment
- Counterpart/linked: BroTown.jsx renderer effect (another slice owns it); R5-2 (context lifecycle), R5-4 (render-throw streak), picsOnce.js restoreAllPictures (8 s cap), entityRenderer prewarm uploads, wheelTrial.js `_said`
- Concerns:
  - [race] (medium confidence) A cleanup that runs while an init is still pending finds pixiRef.current null and destroys nothing; the stale init later resolves and assigns itself (BroTown.jsx:4002-4008 has no "is this still my canvas/epoch" check). Scenario A: a black-screen rebuild on an iPhone; the new init waits on restoreAllPictures (up to 8 s, picsOnce.js:209-215, ON by default picsOnce.js:50) + app.init; the player flicks to another app and back; 600 ms later wsClient sees `__pixiActive === false` (set by the cleanup, BroTown.jsx:8419) and calls _rebuildRenderer('renderer dead on resume') (wsClient.js:5071-5073); more than 5 s have passed so the debounce lets it through (BroTown.jsx:4145) -> glEpoch bump -> cleanup with nothing to destroy -> a third init. The second and third inits then both resolve and both assign: whichever lands LAST owns pixiRef.current (if it is the stale one, the game draws into its detached canvas and the screen stays black until the watchdog rebuilds), and the other is never destroyed: a whole WebGL context, its stage, its TileRenderer left in `_liveTileRenderers` (tileRenderer.js:207, 290), with `_appRef`/registerPrewarmRenderer pointing at whichever init resolved last. Scenario B: backToMenu during a pending init (bootPhase -> 'login' is a dependency, BroTown.jsx:8422): the stale init sets `__pixiActive = true` while the door is up, and the next join's effect sees pixiRef.current set and skips init (BroTown.jsx:4001) -> the game draws into the old detached canvas, the new canvas stays unpainted until the watchdog strikes and rebuilds. Evidence: BroTown.jsx:4001-4008, 4073, 8401-8421; pixiRenderer.js:311-315. Docs: none found on a pending-init cleanup; the 5 s window is v2.3.3890 (BroTown.jsx:169, 4145-4170).
  - [leak] (medium confidence) The module-level handles above are set at birth and never cleared by destroy() (pixiRenderer.js:924-964): between a destroy and the next birth (seconds: the 8 s restore cap) they point at a destroyed renderer, and `_appRef` keeps the destroyed Application reachable until the next init. Most uses are render-driven (safe while no renderer draws), but event-driven ones are not: an equip change in that window runs uploadBakedTextures(_prewarmRenderer) on the dead one (entityRenderer.js:4577-4595; it returns harmlessly only because renderer.texture is gone, :4254-4258). `wheelRendererSaid` is a page-lifetime latch (wheelTrial.js:260-266): a ground worker started between renderers does not wait for the new renderer's word. The per-renderer QA globals made in initPixiRenderer (`__btBlankStage` :321, `__btLightFx` :384, `__btSilhouettes` :482, `__btFarmWorld` :501, `__btArenaWorld` :506) are not removed by destroy either, so each keeps the old renderer's closure scope (its systems, `app`) reachable until the next init overwrites it -- a long wait on the door after backToMenu -- the same class as the minimap probe TRAPS §139 fixed (minimapRenderer.js:1063-1069, 1140). Evidence: pixiRenderer.js:207, 315, 321, 324, 345, 357-372, 384, 482, 501, 506. Docs: TRAPS §139's rule "A renderer object's destroy() must undo what its constructor subscribed to" (docs/TRAPS.md:5486-5487) -- the bakes, listeners and minimap probe were fixed under it; these handles were not.
  - [opacity] (high confidence) Birth installs ~20 global patches and handles in a fixed order with each failure swallowed (pixiApp.js:704-748, pixiRenderer.js:324-397); the order is load-bearing (v2.3.3447: "built here after the palette's", pixiRenderer.js:369-372; v2.3.3883 "after both", :374-376) and lives only in comments.
- Making it explicit: a renderer generation counter: `const gen = ++_rendererGen` at init, every assignment and every module handle registered under `gen`, destroy() resets the handles it owns, and the caller's `.then` drops a renderer whose gen (or canvas) is no longer current (destroying it).

## R5-2 · The WebGL context: asked for, lost, restored, judged on a tab's return
- Area: rendering
- Verdict: watch
- Why: the context's phase is a handful of page-global stamps written in four files (two loss listeners on every canvas, BroTown's rebuild, wsClient's resume probe) and read in this slice to decide depth buffers, map reloads and whether the ground is kept.
- Key files: src/rendering/pixiApp.js:658-672, src/debug/crashTrap.js:286-320, src/rendering/pixiRenderer.js:211-228, src/rendering/pixiRenderer.js:975-993, src/networking/wsClient.js:5064-5110
- Entity: the canvas's WebGL context (one per canvas epoch)
- State lives in: `window.__btGlLostAt` (crashTrap.js:309; zeroed per canvas BroTown.jsx:4138), `window.__btLastGlRebuild` (BroTown.jsx:4200, 4204), `window.__btNoStencil` counter (BroTown.jsx:4051-4052; read pixiApp.js:645), `window.__btCanvasFallback` / `__btPixiInitFails` (BroTown.jsx:4020-4033, 4103-4106), `window.__btGlRebuildOwed` timer (BroTown.jsx:4163-4170), the canvas's own `getContext` patch while app.init runs (pixiApp.js:638-656, 727-732), `_groundKeep` counters (pixiRenderer.js:227-228)
- States: unasked, asked-without-depth (patched getContext), live, lost (event seen, preventDefault asked for restore), restored-in-place (never trusted: "restore is not survivable"), rebuild-owed, superseded (old canvas torn down)
- Transitions:
  - createPixiApp: unasked -> asked (getContext patched to depth:false unless `__btNoStencil` or ?depthbuf) -> live; patch removed in finally (pixiApp.js:638-656, 726-732)
  - no stencil buffer: live -> remade once a page with Pixi's default attributes; `__btNoStencil` then stays >= 1 for the page (BroTown.jsx:4049-4058; pixiApp.js:641-645)
  - webglcontextlost (connected canvas): live -> lost; `__btGlLostAt = now`; a rebuild 2.5 s later, restored or not (crashTrap.js:288-314)
  - webglcontextlost also hits createPixiApp's own listener, which records 'gl-context-lost' with NO isConnected test (pixiApp.js:666-669)
  - tab return 600 ms: renderer gone -> rebuild; fallback -> rebuild; lost-since-last-rebuild -> rebuild; context lost now -> wait 1.5 s -> rebuild or forceRefresh (wsClient.js:5064-5110)
  - forceRefresh on a healthy context: the Wheel's ground is kept unless `?groundkeep=0` / off_groundkeep / a loss since the last rebuild; any other zone's ground is rebuilt (pixiRenderer.js:975-993, tileRenderer.js:407-410)
- Guards that read it: `_lostSinceRebuild()` (pixiRenderer.js:224-226), wsClient's resume ladder (wsClient.js:5071-5092), tileRenderer `_forceImageReload = !!window.__btLastGlRebuild` (tileRenderer.js:383), the rebuild debounce and owed timer (BroTown.jsx:4145-4170)
- Counterpart/linked: R5-1 (the renderer it lives on), crashTrap.js (watchContextLoss), BroTown.jsx black-screen watchdog, R5-10 (`_forceImageReload`)
- Concerns:
  - [divergence] (medium confidence) The two loss listeners on each canvas disagree on teardown: crashTrap's ignores a loss on a detached canvas because "Pixi's own destroy() calls loseContext() on the OLD canvas during an epoch rebuild" (crashTrap.js:289-294), but createPixiApp's own listener (v2.3.1383) has no such test (pixiApp.js:666-669). So every rebuild's teardown can write a synthetic 'gl-context-lost' (and its 'gl-context-restored') into the 16-entry crash ring (crashTrap.js:133-137), with a memory reading (_MEM_KINDS, crashTrap.js:117) and an upload flush (not _QUIET, :144) -- pushing real evidence out of the ring the v2.3.773 note grew it to protect, and making each rebuild read as a second loss in the field telemetry. Evidence: pixiApp.js:666-672, crashTrap.js:117, 129-145, 289-294. Docs: crashTrap v2.3.773 note only.
  - [persistence] (low confidence) `__btNoStencil` is a page-lifetime latch: after one stencil-less context every later context on the page keeps the depth buffer (~11-20 MB on a 3x iPhone, pixiApp.js:623-637). Deliberate per the v2.3.3313 note (pixiApp.js:641-644), but a loss-heavy session (the very one short of memory) pays it for good.
  - [opacity] (medium confidence) `_lostSinceRebuild()` inside forceRefresh (pixiRenderer.js:219-226) duplicates the wsClient ladder's own `__btGlLostAt > __btLastGlRebuild` test (wsClient.js:5085-5088), which already rebuilds before forceRefresh is reached; the two copies of "was the context lost since the last rebuild" must stay in step by hand.
- Making it explicit: one `glLife` module owning {epoch, lostAt, rebuiltAt, owed, noStencil} with `onLost(canvas)` (one listener, the isConnected rule once), `wasLostSinceRebuild()` and `noteRebuild()`; pixiApp, crashTrap, wsClient and BroTown call it instead of writing window stamps.

## R5-3 · One frame's passes: the camera put on whole device pixels, and your place lent to the draw
- Area: rendering
- Verdict: fine
- Why: update() moves S.player by under half a device pixel for the duration of the world passes and puts it back, a two-phase mutation of game state guarded by an exact-equality check, with every pass between wrapped.
- Key files: src/rendering/pixiRenderer.js:582-700, src/rendering/pixiRenderer.js:829-833, src/rendering/pixiRenderer.js:285-292
- Entity: the local player's position (S.player.x/y) and the world container's offset during one update()
- State lives in: `selfShift`/`selfX`/`selfY`/`selfDX`/`selfDY` locals (pixiRenderer.js:691-697), `_camSnapOff` lazy latch (:285-292), `_camProbe` (:296), per-system once-latches `update._tileErr`, `_wobjErr`, `_farmErr`, `_arenaErr`, `_entityErr`, `_effectsErr`, `_lifeErr`, `_worldFxErr`, `_ambientErr`, `_silErr`, `_depthErr`, `_swimErr`, `_jumpErr`, `_rideErr`, `_emoteErr`, `_lightErr`, `_miniErr` (:718-834), `update._poolSweepAt` 5 s sweep clock (:893)
- States: unshifted -> shifted (world passes run) -> restored; per system: quiet -> has-thrown (logged once, never again for that renderer)
- Transitions:
  - frame start with snap on: unshifted -> shifted (S.player.x/y += selfDX/DY) (pixiRenderer.js:691-697)
  - after lightFx: shifted -> restored, only if S.player is the same object and still exactly at the shifted value (:832)
  - a system throws: quiet -> has-thrown (console once; the frame goes on) (:718-834)
  - every 5 s: texture pool sweep (:893)
- Guards that read it: the restore's identity/equality test (:832); TRAPS §231's rule that no renderer writes the player's place
- Counterpart/linked: TRAPS §231 (docs/TRAPS.md:7761-7789), sharpPixels' unsnapped figures, renderFrame.js (the caller), R5-4
- Concerns:
  - [stuck] (low confidence) One statement between the shift and the restore is not wrapped: `else if (silhouettes.recs.size) silhouettes.clear();` (pixiRenderer.js:767). A throw there leaves update() with the player still moved by the sub-pixel shift, carried into the next simulation tick; repeated each frame it would drift him. Reachable only when silhouettes are held outside the Wheel (onZoneChange already clears them, :515), so practically unreachable. Evidence: pixiRenderer.js:697, 767, 832. Docs: TRAPS §231.
  - [opacity] (low confidence) The has-thrown latches are per renderer and never reset, so a second, different failure in the same system is silent for the renderer's life; only app.render's throw reaches the crash log (:851-883).
- Making it explicit: not worth it beyond wrapping line 767 (or passing a shifted copy of the player to the passes instead of moving the real one).

## R5-4 · A world that will not draw: the render-throw streak, the heal, the one rebuild
- Area: rendering
- Verdict: watch
- Why: two copies of "90 throwing frames in a row -> one rebuild" (one on the renderer's update function, one on S) fire only on exactly the 90th frame, so a rebuild request swallowed by the 5 s debounce is never asked again by this path.
- Key files: src/rendering/pixiRenderer.js:844-888, src/game/renderFrame.js:44-71, src/ui/BroTown.jsx:4139-4214
- Entity: the live renderer while app.render() or update() throws every frame
- State lives in: `update._renderStreak` (pixiRenderer.js:844-846, per renderer), `update._renderErr` once-latch (:851-852), `S.__pixiErrStreak` (renderFrame.js:46, 67, on S: survives a rebuild), `window.__pixiUpdateErrLogged` (renderFrame.js:48-49, reset at BroTown.jsx:4208)
- States: drawing, throwing(n<90), rebuild-asked (n==90), throwing-past-90 (no more asks), healed (a good frame resets)
- Transitions:
  - app.render throws: drawing -> throwing; healAfterRenderThrow resets masks/filters (pixiRenderer.js:845-850)
  - 90th consecutive throw: -> rebuild-asked via window._rebuildRenderer (pixiRenderer.js:885-887; renderFrame.js:67-69)
  - 91st+: no further ask (deliberate `===`, renderFrame.js:61-66)
  - one good frame: -> drawing (pixiRenderer.js:844; renderFrame.js:46)
- Guards that read it: `_rebuildRenderer`'s 5 s window, which owes a later rebuild only when the context was lost again (BroTown.jsx:4145-4170)
- Counterpart/linked: R5-1, R5-2, the black-screen watchdog (BroTown.jsx:8862-8905) as the floor, renderHeal.js
- Concerns:
  - [stuck] (medium confidence) If the 90th throw lands inside 5 s of a previous rebuild (a rebuilt renderer that keeps throwing on a freed picture), `_rebuildRenderer` returns without rebuilding and owes nothing unless `__btGlLostAt > __btLastGlRebuild` (BroTown.jsx:4145-4170) -- a throw is not a loss. The streak then climbs past 90 and this path never asks again; recovery waits for the watchdog's dark-screen strikes (two after a first lit frame, ~10 s each) or a reload. Evidence: pixiRenderer.js:885-887, renderFrame.js:67-69, BroTown.jsx:4145-4170. Docs: renderFrame v2.3.773 note says the `===` is deliberate ("can't loop"); the interaction with the v2.3.3890 debounce is not discussed.
  - [divergence] (low confidence) The same rule is kept twice with different lifetimes: `update._renderStreak` dies with the renderer, `S.__pixiErrStreak` lives on S, so after a rebuild the two count from different places.
- Making it explicit: one `renderHealth` record {streak, askedAt} shared by both throw sites, asking again after the debounce window has passed (at most once per window).
