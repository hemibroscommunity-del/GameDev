# T2: the other studios (ground, objects, style)

Slice: public/tools/ground/{app,prompts}.js, public/tools/objects/{app,atlas,catalog,prompts,sheets}.js,
public/tools/style/{app,bible,candidates,process,quant256,scene}.js. All are owner-only browser tools
(no server counterpart); their "counterparts" are the game's ground worker and the files a session
unpacks into public/world/. prompts.js (both), bible.js, catalog.js, candidates.js, quant256.js and most
of process.js are pure functions or static tables (noted where a table drives a machine below).

## T2-1 · Ground Studio picture slots (upload, keep, finish, remove) and the game reading them
- Area: tools
- Verdict: watch
- Why: each swatch version lives in five in-memory maps plus two IndexedDB stores that are written in sequence with awaits between, and the game's worker reads the same stores with different merge rules.
- Key files: public/tools/ground/app.js:334-353, public/tools/ground/app.js:244-283, public/tools/ground/app.js:355-390, public/tools/world/core/ground-worker.js:772-795

- State lives in: `S.raw` / `S.prep` (app.js:116), `S.tiles` / `S.edges` / `S.blends` (app.js:117,124,128), `S.decoded` LRU (app.js:117, cap DECODED_KEEP app.js:102), IndexedDB 'raw' and 'prep' of 'brotown-ground-studio' (app.js:70)
- States: empty, uploaded (raw+prep in memory), stored (raw+prep in IndexedDB), finished (tile/edge/blend entry), unpacked (in `S.decoded`), removed
- Transitions:
  - file input change: empty → uploaded → stored → finished (app.js:717-722 → addPicture app.js:341-345)
  - Remove button: finished → empty, memory first then store (app.js:734 → removePicture app.js:350-352)
  - page load: stored → uploaded → finished (loadAll app.js:363-389)
  - restore zip: any → stored/finished, MERGED over what is here (restoreZip app.js:1359-1382)
  - preview needs pixels: finished → unpacked, oldest evicted past 16 (pixelsOf app.js:314-325); finalize drops the unpacked copy (app.js:248,268,287)
  - palette change: every slot re-finished (finalizeAll app.js:300-303, from app.js:345,352,1382,1428)
- Guards that read it: card chip and Replace/Remove buttons read `S.prep.has` (app.js:657,715,731); export needs raw AND prep AND a tile (app.js:1266-1268); the busy overlay (index.html:111, fixed inset 0) is the only thing stopping two uploads overlapping
- Counterpart/linked: the game's ground worker reads this same 'prep' store and 'misc' (ground-worker.js:772-791, T1 slice); tools/world/add-ground-pictures.mjs drives this page headless; T2-2 (stale marks), T2-3 (remake stamp), T2-6 (boot)
- Concerns:
  - [divergence] (medium confidence) The worker replaces the game copy's entry for an id with the studio's whole entry whenever this browser's studio holds ANY version of it (`out[id] = { from: 'studio', vers: mine[id] }`, ground-worker.js:790), per id, not per version. The studio card then says "in the game: A + B" (app.js:665-669) while the owner's game shows A only. Evidence: ground-worker.js:776-791. Docs: WORLD-MAP-PIPELINE.md:3503-3507 documents "studio first, newest first", not the per-id replace.
  - [persistence] (medium) addPicture puts the slot in `S.raw`/`S.prep` before the two awaited IndexedDB puts (app.js:341-344). A put that fails (Safari quota) leaves memory ahead of the disk: the card's chip and "Replace…" say the version is made (app.js:657,715) but finalize never ran (no tile), the toast blames the picture ("That picture could not be read", app.js:727), and a reload silently loses it. Evidence: app.js:341-345, 727. Docs: none found.
  - [leak] (low) `S.decoded` is capped (16, app.js:324) and old preview canvases are released (app.js:496); the style key's object URL is never revoked (app.js:403), one per load: fine.
  - [persistence] (low, latent) Every studio database opens at version 1 and creates its stores only when the database is first made (`indexedDB.open(name, 1)`, world/store.js:28-29). A store added to STORES later (app.js:70; objects/app.js:70) would never be created in an existing browser, and every get/put on it would throw. Nothing has needed one yet.
  - Dormant parts: versions E (edge pieces) and M (blends) are kept, zipped and restored, but shown and laid only with ?edgepieces / ?blends (app.js:79, 87; the worker likewise, ground-worker.js:780-782).
- Making it explicit: one `slot = { raw, prep, tile, state }` record per key written in one place, store first then memory; worker merge per version.

## T2-2 · Ground Studio "made from an older prompt" marks (brief and time stamps)
- Area: tools
- Verdict: needs-thought
- Why: the stale mark is stamped per picture version but the zip carries one stamp per swatch and a restore rewrites every time stamp, so the mark does not survive the documented move to another browser.
- Key files: public/tools/ground/app.js:1273-1276, public/tools/ground/app.js:1348-1370, public/tools/ground/app.js:685-688, public/tools/ground/app.js:1015-1025
- Entity: each saved picture's provenance (swatch versions A/B/E, blends M)
- State lives in: raw record `brief`, `at` (app.js:339-343; IndexedDB 'raw'); catalog `brief`, `revised`, `accepts` (world/core/ground.js groundCatalog, the static half); zip manifest `swatches[].madeFrom`, `blends[].madeFrom` (app.js:1276,1285)
- States: per version: fresh (brief = catalog brief or accepted), stale (brief differs), legacy (no brief: stale iff the entry has `revised`); per blend: fresh, stale-rewritten (its two grounds' briefs changed), stale-newer (a ground's `at` later than the blend's)
- Transitions:
  - upload: → fresh, stamped with today's brief and `at` = now (app.js:339-343)
  - a code change to a catalog brief: fresh → stale (read at app.js:685-688, 865, 1017)
  - re-upload of a ground: its blends → stale-newer (app.js:1018)
  - restore: → whatever the zip's ONE `madeFrom` for the swatch says, `at` = restore time (app.js:1354-1355, 1366)
- Guards that read it: the card's "Made from an older prompt" (app.js:685-694), the edge block's (app.js:865-869), the blend's (app.js:1016-1025); "The last picture went in" (app.js:1164-1165,1181)
- Counterpart/linked: tools/world/add-ground-pictures.mjs:119 copies `brief`/`madeFrom` into the game manifest the same one-per-swatch way; QA tools/qa/ground-studio.mjs:364-390 tests the marks on a fresh upload only
- Concerns:
  - [persistence] (high confidence in the mechanism, low impact) Export records one `madeFrom` per swatch, the FIRST version with a brief (`vers.map(...).find((r) => r && r.brief)`, app.js:1275), and restore stamps every version of that swatch (A, B and E) with it (`briefOf[m[1]]`, app.js:1366). A swatch whose A was made from today's brief and B from an older one comes back with B marked fresh: its "Make this one again" note is gone in the new browser, and the owner may ship B. The reverse (A old, B new) marks a good B stale. A legacy A (no brief) borrows B's brief and loses its `revised` mark. Evidence: app.js:1275-1276, 1354-1355, 1366, 685-688. Docs: the comment at app.js:1273-1274 assumes one brief per swatch; none found elsewhere.
  - [persistence] (medium) Restore rewrites `at` to the restore time for every picture, in zip order (app.js:1366). The blend's stale-newer test compares a ground's `at` with the blend's (app.js:1018), so restoring a zip that holds a ground but not its blend (or restoring grounds into a browser that already has the blends) marks those blends "was made again after this blend" when nothing changed; "The last picture went in today at…" then shows the restore, not the work (app.js:1164-1165). The manifest carries no `at` to restore from (app.js:1276,1285).
- Making it explicit: carry `madeFrom` and `at` per version in the manifest (`versions: [{ v, madeFrom, at }]`) and restore them as they were.
