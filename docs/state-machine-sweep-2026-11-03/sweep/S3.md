## S3-1 · The room's tick loop: start, pace, stop
- Area: server
- Verdict: watch
- Why: the heartbeat's life (stopped / running / re-armed by the pacer) is split across index.js connect/close, tick.js and tickpace.js, and several tick slots still run outside the per-system `guard`, so one throw can still stop the whole world.

- States: stopped (no interval), running at TICK_RATE, paced (interval < TICK_RATE, re-armed), stopping (last session gone)
- Transitions:
  - first socket accepted: stopped → running, only if `!tickInterval && sessions.size === 1` (index.js:4937 → tick.js:239; `_tickPace` reset to null tick.js:234)
  - a tick whose wanted interval differs: running → paced/back (clearInterval + setInterval, tickpace.js:111-115; only on the real runtime, REAL_TIMERS tickpace.js:61)
  - `tickpace: false`: paced → running at TICK_RATE on the next tick (tickpace.js:101)

- Counterpart/linked: S3-2 (AFK sweep closes sessions from inside a tick), every `_tick*` system; index.js is S1's
- Concerns:
  - [stuck] (low confidence: the gap is real, no throwing input found) v2.3.1562 wrapped each system in `guard` because one throw upstream starved the respawn, but `_tickParties` (tick.js:435), `_tickPlayerRegen` (tick.js:446), `_flushPendingPlayerStates` (tick.js:453), `_tickPingAndAfk` (tick.js:463) and the whole build/send loop (tick.js:505-1286) are still unguarded: a party record that throws (party.js:625-646 walks `p.members`/`p.meta`) aborts the regen, the flush, the AFK sweep and every tick message for the whole room on every tick. `_tickPaceEnd` still runs (finally, tick.js:237) so the interval lives on, sending nothing.   - [race] (low confidence) the stop check reads `sessions.size === 0` after webSocketClose's awaited saves (index.js:6383, 6454); the AFK sweep deletes the session synchronously (tick.js:218), so the interval is cleared later, in the continuation. - Making it explicit: a `tickLoop` object with `start()/stop()/rearm()` owning the handle, the pacer and the counters, and a guard on every slot (including the send loop) so "running" always means "sending".

## S3-3 · The dead/dying pair, with the phone writing `dead` on every move
- Area: wire (both)
- Verdict: needs-thought
- Why: `ps.dead` is set by the worker at a death and cleared at the respawn, but ALSO overwritten by every accepted move from the phone's `dead` field, and the monster AI and the PvP hit loops skip any player whose `ps.dead` is true -- so a phone that says `dead: true` while alive is never targeted or hit, and can still attack monsters.
- Key files: server/src/movement.js:796, server/src/index.js:1941, server/src/combat.js:2321, server/src/combat.js:1202, src/networking/wsClient.js:6046
- Entity: a player (playerState)
- State lives in: `ps.dead` (movement.js:796, index.js:3389/3536, join.js:878 default false, linger/spar), `ps.dying` (index.js:3388/3535), `ps.respawnAt` (index.js:3391/3537), `ps._respawnOwed` (index.js:3596, 3606)
- States: alive, dying (worker: dying+dead, respawnAt set), respawn-owed (dying cleared with no socket), and the illegal combination alive-but-claims-dead (dying=false, dead=true from the phone)
- Transitions:
  - a hit to 0 / stuck-at-zero sweep: alive → dying (`_handlePlayerDeath`, index.js:3383-3391; sweep index.js:3527-3528)
  - respawnAt elapsed: dying → alive, z='town' (index.js:3530-3541); no socket → `_respawnOwed` (index.js:3596, 3606)
  - ANY accepted move: `ps.dead = !!msg.dead` (movement.js:796) -- the phone sends `dead: rpg.hp <= 0` (wsClient.js:6046), so a modded phone sends `dead: true` at will
- Guards that read it: monster candidate list `if (ps.dead || ps.disconnected || !ps.z) continue` (index.js:1941); PvP swing/shot target loop `if (targetPs.dead || ...) continue` (combat.js:2321); pvpextras strikes (pvpextras.js:237, 256, 503); No man's land (nomansland.js:376); monster moves' rings and charge (monstermoves.js:521, 593); storm arcs (monsterstatus.js:379); DOTs put out (monsterstatus.js:510); the attacker side deliberately ignores it for PvE (combat.js:1202-1210) but refuses PvP attackers on it (combat.js:2215)
- Counterpart/linked: index.js death/respawn (S1); combat.js (S4); client death state `S._dying` (wsClient); TRAPS §233
- Concerns:
  - [authority] (high confidence) A phone that sends `dead: true` on its moves while the worker has it alive is dropped from every monster's candidate list (index.js:1941), so no monster targets it, no monster move's ring or charge reaches it (monstermoves.js:521, 593), and burns/poisons are put out (monsterstatus.js:510) -- while `_handleMonsterDamage` deliberately keeps letting it hit monsters (combat.js:1202-1210). In PvP the same claim makes it untouchable by every swing and shot (combat.js:2321, pvpextras.js:503); it only has to send `dead: false` in the same bundle as its own attack (combat.js:2215 reads the attacker's flag) -- wagered duels, the arena and No man's land loot. Nothing on the worker resets `ps.dead` for a live player except a respawn. Evidence: movement.js:796, index.js:1941, combat.js:2321. Docs: TRAPS §233 ("Treat anything a move writes as the phone's claim, not the worker's fact") fixed only the corpse-side gates; docs/specs/item-drop.md "Not done" says other `ps.dead`-only readers were left.
  - [combo] (medium confidence) the other illegal pair, dying=true with dead=false, is reachable too: the move a phone sends while it handles `player_died` still says alive (TRAPS §233), and `_handleMove` takes moves from a dying player (no dying check before movement.js:796), so until the phone's next move after its HP-0 player_state (TRAPS §233: "not dead from then on" for a phone that sends nothing more while dead, i.e. up to the whole five-second respawn window) the corpse is back in the monsters' candidate list (index.js:1941 asks `dead` only) and in the PvP target loop (combat.js:2321). Damage on it is wasted rather than harmful (hits.js:305 will not start a second death), so the cost is monsters standing on a corpse instead of the living. Evidence: TRAPS §233, movement.js:796, index.js:1941.
- Making it explicit: the worker owns one `ps.life` ('alive' | 'dying') and ignores `msg.dead` (or keeps it as `ps._phoneSaysDead` for presentation only); every reader asks `ps.life`.
