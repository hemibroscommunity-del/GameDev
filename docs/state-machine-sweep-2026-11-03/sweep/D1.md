## D1-1 · Elemental statuses on a monster, as this phone predicts them (apply, refresh, tick, collide, expire)
- Area: client
- Verdict: needs-thought
- Why: the server owns statuses and never syncs them, so this local copy runs on its own frame-counted clock and still pays mana and fires collision feedback the worker may never do.
- Key files: src/data/gameSystems.js:4480, src/data/gameSystems.js:4541, src/data/gameSystems.js:4984, src/game/monsterCombat.js:233, server/src/combat.js:1742

- Transitions:
  - own melee hit with a gem: none → applied / refresh (src/game/monsterCombat.js:2157)
  - own arrow with a gem: none → applied (src/game/projectiles.js:1867)
  - legacy lunge (client zone only): applied (src/game/dodge.js:261)

  - server lunge hit (`ability: 'lunge'`): applied (src/networking/gameEvents.js:2756)
  - every monster-loop pass: remaining -= 0.0167 s, DoT tick on real time, expire → delete (src/data/gameSystems.js:4550, 4581; called src/game/monsterCombat.js:233)
  - own hit with a second element: oldest other-element status consumed, streak count+1 or reset, mana +4% (src/data/gameSystems.js:5048-5076; called src/game/monsterCombat.js:2213, src/game/projectiles.js:1875)
  - monster death / respawn: statuses = {} (src/game/monsterCombat.js:209, 289, 2629; src/game/projectiles.js:2282); server monster built with `statuses: {}` (src/networking/wsClient.js:4282)
- Guards that read it: resonance window check (src/data/gameSystems.js:5022), oldest-status pick (src/data/gameSystems.js:4991, 4588), STATUS_DEFS gate on the nova (src/networking/gameEvents.js:1252)
- Counterpart/linked: server's own status clocks and `_collisionResonance` (server/src/combat.js:1742); pip row and auras (entityRenderer, monsterCombat:239); resonance HUD reads `S.player._resonanceStreak` (src/rendering/systems/entityRenderer.js:16605)
- Concerns:
  - [divergence] (high confidence) The phone restores 4% mana on ANY collision once per 3 s (src/data/gameSystems.js:5071, no `resonating` test) and pops "+N MP" in a server zone too (src/game/monsterCombat.js:2463, not gated on `S._serverMonsters`); the worker pays only on a RESONATING collision (server/src/combat.js:1744-1760). A plain collision shows "+N MP" and lifts the bar until the worker's own mana next changes and is echoed (a v2 delta carries only changed fields, so at a steady worker value the phone keeps the extra); near a block boundary the special can light up for a cast the worker then refuses. The server's own note says the client copy is stomped (server/src/combat.js:1739-1741). Docs: none found beyond those comments.
  - [divergence] (medium) `tickStatuses` is always given dt = 16.7 ms a pass (src/game/monsterCombat.js:233), not the frame's time (`S._dtScale` exists, src/ui/BroTown.jsx:4807, and the same loop's movement uses it, src/game/monsterCombat.js:437). At 30 fps a 4 s burn lasts 8 s on screen, so the resonance window, the local streak and the "collision" feedback (ring, sound, certs, codex discovery) come late or for a status the worker already dropped. The number itself waits for the worker (v2.3.2350, src/game/monsterCombat.js:2421-2440), which admits "the client's status clocks can resolve a collision the worker never did". TRAPS §200 is about frame-rate assumptions in tests. Docs: v2.3.2350 comment.
  - [authority] (low) The client's local streak and mastery certs (`masteryEarnCert('first-resonance-hit')`, src/game/monsterCombat.js:2400) are earned off the prediction, not the worker's collision.
  - [combo] (low) `tickStatuses` dereferences `STATUS_DEFS[id].tick` with no guard (src/data/gameSystems.js:4553-4554); every writer today checks the id first (applyStatus returns false on an unknown id, src/data/gameSystems.js:4485), so it holds only while no one writes `m.statuses` directly.
- Making it explicit: drive the local copy from the worker (a status-start/end event, or the tick's status ids) and keep only the drawing here; at least scale dt by `S._dtScale` and gate the mana prediction on `resonating` the way the worker does.
