- Area: rendering (state on the client's monster objects)
- Verdict: watch
- Why: a client-only prediction with no server counterpart; the per-arrow pin keeps a texture reference and a module-wide pixel cache that outlives the zone it was read in.
- Key files: src/game/projectiles.js:436, src/rendering/arrowPin.js:189, src/rendering/arrowPin.js:44, src/rendering/systems/effectsRenderer.js:7061, src/game/monsterCarry.js:23

- States: None; Stuck-unpinned (drawn at feet + stored world offset); Pinned (texel of the frame on screen); Carried (pin re-found on each new frame); Cleared
- Transitions:
  - your own arrow's predicted contact on a live monster, fewer than 12 stuck: None → Stuck-unpinned (projectiles.js:436-447)
  - first draw on a body sprite with readable pixels and opaque art near the line: Stuck-unpinned → Pinned (arrowPin.js:196-211)

  - turned round: shaft angle mirrored (arrowPin.js:221)
  - monster dead (alive false or curHp <= 0): → Cleared (effectsRenderer.js:7062)
  - respawn: server delta (wsClient.js:1305), local AI (monsterCombat.js:214) → Cleared

- Guards that read it: `m.alive !== false && !(m.curHp <= 0) && length < 12` (projectiles.js:441); the bake-or-direct-draw choice (effectsRenderer.js:7082, 7121-7135)
- Counterpart/linked: none on the server (the worker never hears of stuck arrows); R9-3 (the bake of their wounds); hitMaterialOf / hitFxTintOf for the wound's material (arrowWound.js:275-313)
- Concerns:
  - [authority] (medium) a shaft sticks on the phone's OWN predicted contact (projectiles.js:441-447), never on the worker's verdict: a shot the worker judged a miss (latency, a roll, a refusal) still leaves an arrow in the body for the rest of that life, and only the shooter's phone shows any (other phones' arrows never stick: the only push is projectiles.js:446). Cosmetic, but it shows a hit that did not happen. Evidence: projectiles.js:436-447; grep finds no other `_stuckArrows.push`. Docs: none found (CLAUDE.md §5: "a client popup is a prediction; the server's event is the truth").
  - [leak] (low) `_frames` (arrowPin.js:35-41) keeps up to 6 MB of alpha/brightness bytes keyed by texture uid and is only trimmed when a NEW frame is read (arrowPin.js:69-74): after leaving a zone (its textures destroyed, their uids never seen again) the bytes stay for the page's life unless more pins happen. Docs: v2.3.3046 comment (arrowPin.js:36-38) set the cap after the "killing mummies" crash; the exit is not covered.
  - [leak] (low) `sa._pin.tex` holds the frame texture it was pinned on; for a monster carried across a zone's art being freed it points at a destroyed texture (handled: frameData returns null, pinCarry re-snaps). Evidence: arrowPin.js:211-216, 45.
- Making it explicit: a `StuckArrow {state: 'unpinned'|'pinned', pin}` with the cache owned per zone (cleared in effectsRenderer.clear) would close the leak; making the stick server-confirmed would need a wire field.
