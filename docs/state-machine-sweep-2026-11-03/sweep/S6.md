# S6 — the server's economy (market, trades, store/offers, shop, bank, inbox, gambling, dice, reveal bags, salvage, on-chain writer)

Read against handoff rules 5-12 (`docs/ARCHITECTURE-HANDOFF.md:151-230`): storage awaits keep the input gate closed, so the races below are NOT interleavings of two events; they are (a) TRAPS #184's crash model ("each await between two writes is a place a restart can land", `docs/TRAPS.md:6467`), (b) TRAPS #146's oplog-TTL model (stamps pruned after 48h, `server/src/inbox.js:35-40`), or (c) flags that only become visible to a later event after a throw.

## S6-1 · The gift trade (trade_offer / trade_accept relay)
- Area: server
- Verdict: needs-thought
- Why: a single-shot in-memory offer per sender>target pair, settled at accept in one write; still served to any client although honest phones use it only against an old worker, and it never got trade2's PvP fight lock.
- Key files: server/src/trade.js:103-188, server/src/trade.js:203-208, server/src/index.js:6313-6316, server/src/relay.js:66-68, src/ui/panels/InspectPlayerPanel.jsx:257-276
- Entity: one pending gift offer, keyed `sender>recipient`
- State lives in: `this._pendingTradeOffers` Map (server/src/trade.js:114), entry `{offer, fromName, ts, id}` (server/src/trade.js:119-122)
- States: none, offered (pending, ts < TTL 120 s), expired, settled (deleted on accept), rejected-at-commit
- Transitions:
  - trade_offer relayed: none/offered → offered (overwrites an earlier offer to the same target, new id) (server/src/trade.js:116-125)
  - trade_accept: offered → deleted before validation (single-shot) (server/src/trade.js:128-130); stale/forged → dropped silently (server/src/trade.js:135)
  - accept, sender gone or short: → trade_reject to the accepter (server/src/trade.js:131-148)
  - accept valid: debit sender + `_creditLiveTogether`, one write (server/src/trade.js:150-174); else the old one-by-one path (server/src/trade.js:175-185)
  - tick: offered → deleted when ts > TTL (server/src/trade.js:203-208, server/src/tick.js:379)
- Guards that read it: `Date.now() - pending.ts > TRADE_OFFER_TTL` (server/src/trade.js:135); `_invCount` own-property gate (server/src/trade.js:147). No `_bagLockedByFight`.
- Counterpart/linked: client TradePanel / IncomingTradePanel, opened only when the worker lacks `caps.trade2` (src/ui/panels/InspectPlayerPanel.jsx:262-276); trade2 (S6-2) shares `_sanitizeTradeOffer`; nomansland.js `_bagLockedByFight`; `trade_reject` is a plain relay (server/src/relay.js:68) and does not delete the pending offer.
- Concerns:
  - [guard-drift] (medium confidence) v2.3.3183 added the "nothing leaves the bag in a fight with a player" test to trade2's confirm because "a trade to a friend emptied a losing bag before the killer's pile" (server/src/trade2.js:229-234), and nomansland.js says "every road out of the bag" now asks it (server/src/nomansland.js:234-246). The gift lane does not: a modified phone losing a PvP fight sends `trade_offer` of its whole bag and gold to a friend whose phone auto-sends `trade_accept`; `_interceptTrade` moves it with no fight check on either side, and the killer's pile is empty. The relay allowlist still carries both types (server/src/relay.js:66-67), and no live flag retires the lane. Evidence: server/src/trade.js:127-174. Docs: server/src/nomansland.js:234-246 (the rule), none found for this lane.
  - [divergence] (low) A target that pressed Decline (relayed `trade_reject`) can still send `trade_accept` within 120 s and the server settles it; the sender's popup already said "declined". Only a modified client does this, and the sender did offer the goods. Evidence: server/src/trade.js:128-135 (no reject branch; only offer/accept are intercepted, server/src/index.js:6313). Docs: none found.
  - [persistence] (low) The `else` branch (a party not in the room) is still the old two-batch save-then-credit; unreachable in practice because the accepter just sent the message and the sender is checked live. Evidence: server/src/trade.js:175-185. Docs: TRAPS §184.
- Making it explicit: retire the lane behind a live flag (the honest client already prefers trade2), or route it through the same `_bagLockedByFight` gate; the machine itself (one map, one TTL, one single-shot delete) is small.

- Area: wire (both)
- Verdict: needs-thought
- Why: a five-flag in-memory session (state/ready/confirmed/changedAt/weapons) whose weapon lane is escrow-at-stage in storage while items/gold/pets are validate-at-commit; the weapon deliveries are awaited AFTER the one-write commit, so a restart in between half-applies the trade.
- Key files: server/src/trade2.js:214-376, server/src/trade2.js:541-671, server/src/trade2.js:124-173, server/src/index.js:5807-5845, server/src/index.js:6436

- States: invited (one-sided invite), open/offer stage (not both ready), open/review stage (both ready), open/one-confirmed, committing, done, cancelled (declined | disconnected | expired | party-gone | insufficient | pet-gone | pets-full)
- Transitions:
  - trade2_open A→B: none → invited (server/src/trade2.js:170-172); B→A within INVITE_TTL: invited → open/offer (server/src/trade2.js:144-166)
  - trade2_set / trade2_pets / stage / unstage weapon / pet rename: any open → open/offer, all ready+confirmed reset, changedAt=now (server/src/trade2.js:182-194, 496-503, 588-594, 614-621, 512-523)
  - trade2_ready {ready}: toggles ready[me] only (server/src/trade2.js:203-212)
  - trade2_confirm: needs both ready + 2.5 s since changedAt + no PvP fight (server/src/trade2.js:225-234); one confirm → open/one-confirmed; both → commit (server/src/trade2.js:235-376)
  - commit: validate both → debit both → pets move → state='done', session deleted → `_creditLiveTogether` (server/src/trade2.js:256-331) → THEN each staged weapon credited + its escrow row deleted, one await each (server/src/trade2.js:356-367) → late pets by mail (server/src/trade2.js:368-374)
  - trade2_cancel / disconnect / tick idle (SESSION_TTL 5 min) / invite TTL 60 s: open → cancelled, weapons refunded fire-and-forget (server/src/trade2.js:113-122, 419-460)
  - join (rate-limited 5 min): orphan `trade2wpn:` rows with no live session refunded unless the deliver stamp exists (server/src/trade2.js:650-671, server/src/join.js:1603)
- Guards that read it: `_t2SessionFor` (state==='open') (server/src/trade2.js:68-74); not-ready / cooling / fight gates (server/src/trade2.js:225-234); busy gate (server/src/trade2.js:136); `_t2Cancel` single-shot (server/src/trade2.js:114)
- Counterpart/linked: client TradeWindowPanel is a pure renderer of `trade2_state` (src/ui/panels/TradeWindowPanel.jsx:44-90, src/networking/gameEvents.js:4921-4960); `_bagLockedByFight` (nomansland.js); pets record (petbook.js `_petSellable/_petbookTake/_petbookGive`); inbox primitives (S6-4).
- Concerns:
  - [persistence] (medium confidence) A trade with weapons is NOT one write: items/gold/pets commit in `_creditLiveTogether`, and the session is already deleted from memory, then each weapon is delivered with its own awaited `_creditPlayer` + `storage.delete`. A restart in that gap leaves the `trade2wpn:` rows with no deliver stamp, and the next join's `_trade2WpnSweep` REFUNDS them to their original owners: e.g. A's 4 weapons for B's 100k gold → A keeps the gold AND the weapons. Evidence: server/src/trade2.js:329-367 (deliveries after `await together`), server/src/trade2.js:658-667 (sweep refunds any row lacking the deliver stamp). Docs: TRAPS §184 names "a staged weapon returned twice" but the v2.3.3294 fix covers only items/gold/pets (server/src/trade2.js:323-328).
  - [persistence] (low) `_t2WpnSeq` restarts at 1 after a deploy, and the escrow key is `trade2wpn:<pid>:<seq>`. If an orphan row from the previous lifetime has not been swept (the sweep is fire-and-forget, `try{}catch{}` best-effort, and once it has run it will not run again for 5 min), a new stage by the same player that draws the same seq OVERWRITES the orphan row: that weapon is never refunded. Evidence: server/src/trade2.js:573, 579, 652-653, 670. Docs: none found.
  - [combo] (low) `trade2_ready {ready:false}` (the review screen's Back) leaves `confirmed[me]` true, so ready=false+confirmed=true is reachable; on re-Ready the pair is back on review with me already accepted, and the other side's single Accept commits. The client does draw "Accepted ✓" so it is visible, but Back does not withdraw consent. Evidence: server/src/trade2.js:203-212 vs 188-190; src/ui/panels/TradeWindowPanel.jsx:1466-1469. Docs: docs/specs/trading.md (no Back rule found).
  - [stuck] (low) A second login that supersedes the socket skips webSocketClose (server/src/join.js:759-770), so the session stays open against the new tab, which has no window until the other side edits (broadcast reaches the new socket) or the 5-min idle TTL. Not value-losing. Evidence: server/src/trade2.js:429-434, server/src/index.js:6436.
- Making it explicit: a declared `{offer, review, committing}` stage per session with one transition table, and the weapon deliveries folded into the same write as `_creditLiveTogether` (or the deliver stamps written there), would close the gap.

## S6-3 · The order book's order (mkt_order: rest → match | cancel | expire)
- Area: server
- Verdict: needs-thought
- Why: the match path saves the taker's escrow and then awaits three separate credits and a delete, and the wake-time rebuild treats ANY one settle stamp as "settled, delete": a restart between the legs loses the taker's escrow or the seller's pay.
- Key files: server/src/market.js:268-436, server/src/market.js:88-122, server/src/market.js:438-489, src/ui/panels/buildings/ExchangePanel.jsx:660 (live: the General Store door, src/data/wheelBuildingDoors.js:46)
- Entity: one resting order (buy escrows gold, sell escrows a stash weapon)
- State lives in: storage `mkt_order:<id>` (server/src/market.js:408); in-memory `this._mktIndex` buckets + `this._mktOrderCounts` (server/src/market.js:90-91); `order.expires` (server/src/market.js:341); `this._mktLastSweep` (server/src/market.js:475-476); oplog stamps `settle:<makerId>:item|gold|diff`, `refund:<id>`, `mktunwind:<id>`
- States: escrowed-unwritten (taker, in memory only), resting, matching (removed from index, credits in flight), settled (record deleted), cancelled/expired (refund then delete), crash-leftover (record + some stamps)
- Transitions:
  - place, no cross: escrow (splice/debit + `_saveRpg`) and the record put in one synchronous run → resting (server/src/market.js:305-328, 389-408); put throws → unwind (server/src/market.js:409-434)
  - place, crosses a maker: taker escrow saved (server/src/market.js:327) → maker out of index (server/src/market.js:358) → await weapon credit (379) → await gold credit (380) → await diff credit (382) → await delete (384) → price history (385)
  - cancel: out of index → refund → delete (server/src/market.js:438-453)
  - lazy expiry on any market HTTP call, ≤ once a minute: expired → refund → delete (server/src/market.js:473-489, 195-196)
  - wake rebuild: record with any of `settle:item`, `settle:gold`, `refund` stamped → deleted, else re-listed (server/src/market.js:101-106)
- Guards that read it: `_mktRefund` refuses over a settle stamp (server/src/market.js:464-465); max 10 orders (server/src/market.js:301); `_bagLockedByFight` (server/src/market.js:299)
- Counterpart/linked: client ExchangePanel trusts `settled:true` (rule 19); the Auction House (S6-5) copied this design and added intent markers because of it (server/src/store.js:49-70, 994-997); inbox primitives (S6-4).
- Concerns:
  - [persistence] (medium confidence) A crossing placement is four write batches. Restart after the taker's save but before the weapon credit: the taker's gold (taker-buy) or weapon (taker-sell) is gone and nothing names it (the taker's order was never stored), while the maker's untouched record re-lists. Restart after the weapon credit but before the gold credit: the rebuild sees `settle:<id>:item` and DELETES the record, so the seller is never paid (and a taker-buy's price-improvement refund is lost the same way). Evidence: server/src/market.js:327, 379-384 (awaited legs), server/src/market.js:101-106 (any stamp → delete, no "finish the missing leg"). The suite only simulates a lost DELETE (server/test/market.test.mjs:256-266). Docs: TRAPS §184 / §147 (the rule), handoff rule 7; the trades were fixed in v2.3.3294 but this path was not.
  - [persistence] (low) Convergence leans on oplog stamps, which `_opPruneMaybe` deletes after 48 h of an occupied room (server/src/inbox.js:35-40). A crash leftover (credits stamped, delete lost) that is not rebuilt within that time is re-listed with its weapon already delivered: it can be bought again or refunded on expiry. The rebuild runs only on the first `/api/market` call after a wake (server/src/market.js:195). Docs: TRAPS §146 ("the oplog stops a retry inside 48 hours; it is not the record").
  - [stuck] (low) `_mktIndex` is set to an empty Map BEFORE the awaited list (server/src/market.js:89-92); a throw in the list or an `_opSeen` leaves a partial book for the life of the DO: resting orders invisible, never matched, never expired, the 10-order cap blind. Docs: none found.
  - [guard-drift] (low) Expiry is soft: the matcher never reads `o.expires`, and the sweep runs at most once a minute, so an order that expired seconds ago still fills. Evidence: server/src/market.js:350-354 vs 480. Docs: none found.
- Making it explicit: an intent marker on the maker's record (`rec.match = {takerId, legs}`) written in the same run as the taker's escrow, and a rebuild that finishes the missing legs, as store.js's `rec.sale` does.

## S6-4 · A credit's life: live, parked in the mailbox, drained at the join (inbox + oplog)
- Area: server
- Verdict: watch
- Why: the one funnel 49 producers pay through; well defended since v2.3.3294 (stamp with the payment, `_inboxSerial`, `_opInFlight`), but its idempotency is a 48-hour journal while several callers' records live longer, and an online player's parked weapon waits for the next join.
- Key files: server/src/inbox.js:243-336, server/src/inbox.js:519-615, server/src/inbox.js:274-297, server/src/inbox.js:173-213, server/src/inbox.js:648-712
- Entity: one credit entry `{opId, source, kind, payload, note}` for one player; the player's mailbox `inbox:<pid>`; the journal `oplog:<opId>`
- State lives in: storage `inbox:<pid>` (server/src/inbox.js:520), `oplog:<opId>` (server/src/inbox.js:105-107); memory `this._opInFlight` Set (server/src/inbox.js:246-253), `this._inboxChains` Map (server/src/inbox.js:553-561), `this._opPrune` cursor + `this._lastOpPrune` (server/src/inbox.js:175-211); per-player marks `ps._apOnceFailed/_apOnceDirty` (server/src/inbox.js:63-73)
- States: unseen → in flight (memory) → delivered (live state saved + stamped) | inboxed (mailbox + stamped) → drained (delivered at join) | still queued (weapon/gear stash full, pet book not loaded/full, achievements not loaded) ; stamp: fresh → pruned after 48 h
- Transitions:
  - `_creditPlayer`: opId already in flight → 'dup' (server/src/inbox.js:247); stamp seen → 'dup' (server/src/inbox.js:300); applies live + save + stamp in one run → 'delivered' (server/src/inbox.js:321-328); else mailbox append + stamp in one run → 'inboxed' (server/src/inbox.js:331-335)
  - `_creditLiveTogether`: all recipients live and gold/item only → apply all, save all, stamp all in one run; else null and the caller goes one by one (server/src/inbox.js:274-297)
  - join drain (serialized per box): each entry applied or kept; player save and box rewrite in one run (server/src/inbox.js:567-615)
  - mailbox at 200: gold/item merge into an existing entry (server/src/inbox.js:524-542)
  - tick slot: one 500-key page of the prune per 3 s, hourly anchor (server/src/inbox.js:173-213)
- Guards that read it: `_opSeen` (every settlement and sweep in the slice), `_applyCreditToPs` returning false = stay queued (server/src/inbox.js:448, 488, 493, 419)
- Counterpart/linked: client `inbox_delivered` (PRIVILEGED); every economy machine in this slice; TRAPS §146/§147/§184.
- Concerns:
  - [persistence] (medium) The journal is pruned at 48 h (server/src/inbox.js:37) while records that converge on it live longer: store listings 7 days (server/src/store.js:140) and the market's 24 h orders, both rebuilt only on the first HTTP call after a wake. Any crash leftover that is not converged within 48 h of an occupied room converges the wrong way (see S6-3, S6-5). Docs: TRAPS §146 states the rule; the callers below do not all follow it.
  - [stuck] (low) A weapon/gear credit to an ONLINE player whose stash is full is parked and only drained at their NEXT join; nothing re-drains when they free a slot mid-session. By design (rule 3), but it reads as "lost" to the player until they relog. Evidence: server/src/inbox.js:321-335, 563-566. Docs: inbox.js header (by design).
  - [race] (low) `_creditPlayer` answers 'dup' to a second caller while the first is still in flight (server/src/inbox.js:247); callers treat 'dup' as done and delete their escrow row (e.g. server/src/trade2.js:633-640, 664-668). If the first call then throws (storage error), the row is gone and the credit never landed. Only reachable on a storage fault. Docs: none found.
- Making it explicit: not worth a rewrite; the one structural fix is making every caller's "paid" record durable on its own (TRAPS §146) instead of leaning on the 48 h journal.

Evidence: server/src/store.js:601, 821, 861, 913, 1002-1029; server/src/storeoffer.js:142. Docs: store.js:982-1001 (the releasing marker's own history).

The rebuild runs only on the first store request after a wake (server/src/store.js:541, storeoffer.js:138). Docs: TRAPS §146.
  - [stuck] (low) A `_stSettle` that throws mid-way leaves `rec.sale` set in memory: hidden from browse, uncancellable, skipped by both sweeps, until a restart's rebuild finishes it. Evidence: server/src/store.js:839-848, 1052. Docs: none found.
  - [combo] (low, documented) A shield or amulet can be listed while worn (no equip message reaches the server for those slots). Evidence: server/src/storegear.js:135-156. Docs: storegear.js header section 2 (an accepted open hole).
  - [stuck] (low) `_stIndex` is set before the paged list (server/src/store.js:429-431); a throw mid-rebuild leaves a partial shelf for the DO's life. Docs: none found.
- Making it explicit: one `rec.phase` field ('resting'|'bidding'|'buying'|'accepted'|'releasing') with a single `_stMay(rec, verb)` guard used by every path, and the paid/refunded facts written into the record in the same run as the money (TRAPS §146), would replace four markers and six guards.
