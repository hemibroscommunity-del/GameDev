# V15 · A player's way in and first minutes (key check, door, creator, joining, the coach's first lessons)
- Verdict: needs-thought
- Severity: medium (players lose the onboarding that tells them to save their Login Key, the only way back to a character: new players on many laptop windows, and everyone already past the Mayor's tutorial. The rest are small glitches: a door sound played twice, a level-up played under a loading screen, a wasted lookup budget, a rare stale Restart, a bounce to the door after a crash reload.)
- Who can trigger it: honest player: (1) on a computer, start a new character in a browser window under about 754 CSS px tall (a 1366x768 or 1536x864 laptop, or any window that is not maximised) and put on the sword and shield: "Your map", "Your quest" and "Save your Login Key" never come; (2) finish the Mayor's tutorial in a browser that never showed the map and quest cards (everyone before today's v2.3.4106): no Login Key card, ever; (3) on a phone, tap Pet House on your farm: the door plays twice; (4) open the character list with several characters the device has no picture for: each one after the first costs two of the 20 account questions a minute; (5) a crash-recovery reload on a slow network: back on the door. Deploy/restart timing only: Settings' Restart losing its answer.
- Summary: Before you play, the page moves through phases: checking your key, the door, the creator, then the world, its loading screen and the coach's first lessons. Each phase lives in a different variable, flag or timer, spread over many files. The real harm is in the first lessons: on many laptop windows the map card counts as "too big", so the quest card and the "Save your Login Key" card never come, and players already past the tutorial never get the Login Key card. The rest are small glitches.
- Key files: src/ui/mobile/QuestCoach.jsx:1379-1386, src/ui/mobile/QuestCoach.jsx:160-188, src/ui/BroTown.jsx:12012-12038, src/ui/BroTown.jsx:11817-12006, src/ui/panels/CharacterPicker.jsx:231-276, src/ui/BroTown.jsx:2168-2171

## The machine
- Entity, and where its state lives: one browser tab's way into the world. The phase is `bootPhase` 'checking' | 'login' | 'create' | null (src/ui/BroTown.jsx:2273), with `showWelcome`/`setShowWelcome` derived from it (2282-2283), `showIntro` (2306), the auto-join latch `_autoJoined` (12012, written only at 12015), `_bootRan`/`_straightInRef` (11815-11816), sessionStorage `bt_play_now` / `bt_resume_now` / `bt_resume`, the address words create/login/noresume (src/ui/keepSwitches.js), `S._rpgFromServer` (BroTown.jsx:12106; src/networking/wsClient.js:3138) and the loading gate's `_worldIn`, opened only by markWorldIn (src/ui/loadingGate.js:39,80-84; src/ui/onboardingPace.js:106). After that comes the coach: the browser record `bt_coach_v1` and its refs (QuestCoach.jsx:1034-1063) and the pacing referee's `_coachUp`/`_coachEndAt` (onboardingPace.js:118-121). Side machines in this cluster: the picker's lookup loop (CharacterPicker.jsx:231-276; `_lookAsked`, src/networking/charRoster.js:141); Settings' `resetStage` (src/ui/mobile/dash/SettingsPanel.jsx:141); the paint editor's canvas (`artId`/`artIdRef`/`doc.id`, src/ui/panels/PlayerPaint.jsx:1060-1110); the level-up bursts (src/ui/levelUpBursts.js); the farm's interaction prompts (BroTown.jsx:15062-15152).
- States:
  - checking: asking the worker whether this key has a character (only on a straight-in reload; otherwise the door paints at once).
  - door ('login'): Continue (the character list) or Create.
  - creator ('create').
  - joining: bootPhase null, joinTown has run, the ocean clip (the loading screen) waits for pictures, the server and the arrival in BroTown. Never declared: it is `bootPhase === null && showIntro`.
  - in the world: the clip has lifted, markWorldIn has run, the loading gate is open.
  - first lessons: the coach walks FIRST_STEPS (mayor, equip, minimap, questPill), then passkey after tut_1 is handed in; after tut_4 only the `anytime` lessons.
  - (broken) in the world without a join: bootPhase null, the latch set, joinTown returned at its pinch gate. No clip, and the gate stays shut.
- Moves:
  - mount: → checking (BroTown.jsx:2273)
  - no straight-in mark: checking → door, with the account check in the background (11952-11976)
  - `?create=1` with a new key: checking → creator (11866-11869); `?login=1`: → door (11873-11875)
  - straight-in mark, and the worker says "has a character": checking → null (11993); any other answer: → door (11995-12003)
  - resume effect on a recovery reload or a fresh snapshot: checking → null at mount, BEFORE the account answer (12282, 12333)
  - door Play on the same key: door → null (12426); on another key: reload with bt_play_now (12460-12464)
  - door Create: reload with `?create=1` (12551-12558) or → creator (12561); creator Back: creator → door (2294-2303)
  - creator ENTER: joinTown() directly (src/ui/panels/NameModal.jsx:1626), which sets null (BroTown.jsx:12195); the auto-join effect then runs joinTown again (12013-12016)
  - bootPhase null with the latch unset: joinTown (12013-12016); a throw: → door (12037); the pinch gate: return with nothing done and the latch left set (12053-12056)
  - joinTown: clip up (12240); clip done: markWorldIn and clip down (12597-12598)
  - coach: player_state lands (wsClient.js:3138) → walking; first steps in order (QuestCoach.jsx:1382); passkey after them and tut_1 (1386); tut_4 handed in → anytime lessons only (1379); retire (1318-1326), which never calls noteCoach(false)
  - Settings Restart: idle → confirm → connecting/sending → the ack's wipe and reload (wsClient.js:1512-1534), or a bare reload after 8 s (SettingsPanel.jsx:200)

## What needs further thought
- Should the "Save your Login Key" card wait for "Your map" and "Your quest" at all? If it should, should those two count as done for a player already past the tutorial, or once the map has been drawn at all? As written today, anyone who missed them never gets the Login Key card.
- On a computer the minimap is twice as big (264 px). Should the map card be allowed to ring something that size? The "too big" rule was written for joystick-sized controls, and the minimap is the one large thing the first steps point at.
- When a crash-recovery reload cannot reach the account check, should the page stay in the world behind the "Reconnecting" veil (the resume road has already committed) instead of going back to the door?
- Making it explicit: one small `door.js` would hold `phase` ('checking' | 'door' | 'creator' | 'joining' | 'world') and one `go(next, why)` that refuses illegal moves (a late account answer cannot send 'joining' back to the door; a refused pinch-zoom goes back to the door instead of leaving the latch set). joinTown would be entered only from `go('joining')`, so the creator's ENTER and the auto-join cannot both run it, and markWorldIn would be the single way into 'world'. For the coach: one table row per lesson {gate, order, finish rule, prerequisites that can finish under the same gate}, plus one exit function that always calls noteCoach(false). For the level-ups: the gate moves into the burst bus (pushLevelUpBurst waits on whenWorldReady), so every setter is covered.
- Quick fixes vs design work: one-line fixes: set the latch inside joinTown after its pinch gate (and go back to the door on a refusal); call noteCoach(false) in the retire branch; reset infoRef when an info card is hidden; mark a row asked before its fetch, or run the queue outside the [roster] effect; give the three farm and Wheel prompts onClick alone (as v2.3.2617 and v2.3.3407 did); gate pushLevelUpBurst on whenWorldReady; run the same cache wipe in Settings' 8 s fallback; build DeviceScreen's reload with keptQuery; delete the dead onExit prop. Needs a decision: the Login Key card's prerequisites and the map card's size rule on computers (both part of today's v2.3.4106 first-steps design); whether a recovery reload with a failed account check stays in the world; whether Restart from a superseded tab may take the character back.
