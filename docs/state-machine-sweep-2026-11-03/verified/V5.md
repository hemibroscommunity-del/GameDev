# V5 · Which character this browser plays: the shared Login Key, each tab's id, the character list and the resume snapshot
- Verdict: needs-thought
- Severity: medium (a player with two tabs on two characters: the first tab turns into the other character and puts the other tab out, or, for a character made before v2.3.3355, into a brand-new level-1 copy with the same name and look that reads as a wipe; the other character is handed copies of the first one's spare armour (usable, not sellable); list rows show the wrong name and level. Nothing is deleted on the server and every key stays in the list.)
- Who can trigger it: honest player, phone or computer: (1) play character A in one tab; (2) open the game in a second tab or window of the same site and Continue as character B (or press Create, or type B's Login Key); (3) go back to the first tab after more than 5 s, or wait for any reconnect (a dropped connection, a worker deploy, the 2-minute idle logout and a touch). Result: the first tab becomes B and the second is put out. The level-1 copy needs A to predate v2.3.3355 (its old key still kept) and the shared key to be old-shaped or gone at that moment (tab 2 still in the creator, B refused for the device, A deleted from the list in tab 2), or the `keys2` switch off. Deploy timing also triggers it: a deploy reconnects every tab at once.
- Summary: A browser keeps the character it plays in one shared slot (the Login Key), but each tab fixes its character id when it starts. Play two characters in two tabs and the slot follows whichever tab switched last. When the first tab reconnects (returning to it after five seconds is enough), it joins with the other tab's key: usually it becomes the other character and kicks that tab; with an older key it makes a new level-1 copy that looks like a wipe. Nothing is deleted on the server.
- Key files: src/networking/wsClient.js:578-599, src/networking/wsClient.js:1475-1496, server/src/join.js:541-553, src/ui/BroTown.jsx:8853-8858, src/networking/charRoster.js:599-614, src/networking/index.js:221-254

## The machine
- Entity, and where its state lives: which character one page of the game plays, and the stores behind it. Per tab (memory): `S.myId`, fixed once at page start (src/ui/BroTown.jsx:1086-1113); `S._joinId`, `S._joinKey`, `S._joinedId` (src/networking/wsClient.js:585, 596, 1555); `S._authRejects` (1476); `S._keyIdAsked`, `S._keyFellBack` (4523, 4546); sessionStorage `bt_resume`, `bt_play_now`, `bt_resume_now` (BroTown.jsx:12190, 11948, 8722). Per site address, shared by every tab: localStorage `bt_passphrase`, `bt_passphrase_prev`, `bt_passphrase_old`, `bt_key_ids` (src/networking/index.js:66-104), the list `bt_chars` (src/networking/charRoster.js:41), `bt_rpg` and the other per-character caches (charRoster.js:47-50), `bt_resume` (BroTown.jsx:12191), `bt_device` (index.js:340-357), the look stores (e.g. src/rendering/traits/headwearCatalog.js:133-154). Per registrable domain (every deploy link of the project): the `bt_chars` cookie with tombstones (src/networking/rosterCookie.js:19-28, 163-186). Server: `auth:<id>` {pfHash, keys, fresh, oldGone, devs} (server/src/join.js:501-553; server/src/loginkeys.js:113-179) and `char:<id>` {name, look} (join.js:596-621).
- States:
  - Door: a key on file, no character chosen, no socket (wsClient.js:311).
  - Playing on an old key: joined with an old-shaped key; the id is worked out from it.
  - New key pending: `key_new` arrived; the old key kept as `bt_passphrase_old` (wsClient.js:2255-2260).
  - Playing on a new key: a join with the new key got in; the old copy removed (wsClient.js:1551-1555).
  - Key moved by another tab (never declared, never detected): the shared key no longer belongs to this page's id.
  - On the other tab's character: the page re-targeted its id at open (wsClient.js:578-584).
  - Refused 'auth': minted once into a new level-1 character, stopped on the second refusal (wsClient.js:1475-1508).
  - Refused 'key': the door asked once, then the old key once, then the key screen (wsClient.js:4517-4561).
  - Superseded: another page joined with the same id; banner, no reconnect (wsClient.js:4646-4649).
  - Resume snapshot fresh (under 10 min) or stale; straight-in wanted (`bt_play_now` / `bt_resume_now`) (BroTown.jsx:12256-12282).
- Moves:
  - page start: no key → adopt the mirror's one row or mint; id = idForKey or worked out (BroTown.jsx:1086-1113).
  - picker row: shared key written, seven caches cleared, reload straight in (charRoster.js:599-614; BroTown.jsx:12423-12465).
  - Create: a fresh old-shaped key minted into the shared slot, reload to the creator; no socket until ENTER (BroTown.jsx:12516-12557; wsClient.js:311).
  - typed Login Key: shared key written, only two caches cleared, snapshot kept, reload straight in (index.js:221-254). WRONG: clears less than the picker.
  - forget the active row: shared key removed (charRoster.js:580-585).
  - every socket open: join = this page's id + the key read NOW; a new key re-targets the id (wsClient.js:578-599). WRONG: no check that the key is the one this page started with.
  - old-key join in (kv 2): `key_new` → New key pending (loginkeys.js:135-179; wsClient.js:2255-2260); a new character's first key is retired at the new one's first use (loginkeys.js:127-131).
  - new-key join in: state_sync → Playing on a new key (wsClient.js:1551-1555).
  - 'auth' refusal of an old-shaped join key: mint into the shared slot, `S.myId` = new id, reconnect (wsClient.js:1475-1496, 4657-4659). WRONG in the two-tab case: this page's own key was never wrong.
  - 'key' refusal: ask the door, fall back to `_old`, or the key screen (wsClient.js:4517-4561).
  - the same id joins elsewhere: Superseded (join.js:758-772; wsClient.js:4646-4649).
  - tab back after more than 5 s, idle "I'm back", a dropped socket: rejoin (wsClient.js:5032-5052, 5118, 4982-4993, 4657-4659).
  - every 30 s in play: snapshot refreshed, and the SHARED key's list row stamped with this page's name, level and id (BroTown.jsx:8813-8858). WRONG: it can be another tab's row.
  - straight-in reload: name and look seeded from the snapshot, whoever wrote it (BroTown.jsx:12256-12313). WRONG: no owner check.
  - MISSING: "the shared key moved under this page" → nothing. No storage listener or BroadcastChannel for it anywhere in src/ (the only channel, crashTrap.js:166-174, is telemetry and assumes one identity).
- Diagram edges:
  - `Door --picker row / typed key, reload--> Playing`
  - `Playing(old key) --join kv 2, key_new--> NewKeyPending`
  - `NewKeyPending --state_sync--> Playing(new key)`
  - `Playing --other tab: picker / Create / typed key / forget--> KeyMoved` !! (this tab is never told)
  - `KeyMoved --rejoin, shared key is new--> OnOtherCharacter` !! (other tab put out, stash merged in)
  - `KeyMoved --rejoin, shared key old or gone, old key kept--> AuthRefused` !!
  - `KeyMoved --rejoin, this character's old key retired--> KeyScreen`
  - `AuthRefused --first time this page--> LevelOneCopy` !! (shared key overwritten)
  - `AuthRefused --second time--> Stopped`
  - `LevelOneCopy --other tab rejoins--> OnOtherCharacter` !! (or a second copy)
  - `OnOtherCharacter --other tab taps Play here instead--> Superseded`
  - `Playing --every 30 s--> OtherRowStamped` !! (wrong name, level, id on another key's row)
  - `Door --typed key, snapshot fresh--> ResumedWithOldLook` !! (until state_sync)
  - `KeyScreen --door names the key's id--> Playing`

## What needs further thought
- Should one browser be able to play two different characters in two tabs at the same time? The docs still say "two tabs in one browser share one identity by design" (docs/specs/identity.md:88-90, docs/ARCHITECTURE-HANDOFF.md:770-771, src/debug/crashTrap.js:166-169), but the character list made two characters in two tabs a two-tap road.
- When a tab finds that another tab switched character, what should it do: keep playing its own character (its key still works on the server), or stop and say "you switched character in another tab" with a Reload button? Today it silently becomes the other character, or makes a new one.
- The gear-stash merge on every join (docs/specs/fresh-start.md:107-116) is already your call; this machine gives an unmodified phone a road into it. Should the server's stash be the whole truth?
- Making it explicit: one identity record per page, `{key, id}`, taken at page start and changed only by this page's own key_new, fallback or mint. The join sends that record, never a fresh read of the shared slot; one check at socket open compares the shared slot with it (same: join; different: another tab moved it, so join as neither and show the "switched in another tab" screen). The heartbeat, joinTown and the 'auth' branch use the page's key. One `switchCharacter(phrase, how)` for the picker, typed key, Create and mint clears one list (CHAR_CACHE_KEYS, the session copies, the drawings); the snapshot and `bt_rpg` carry the id they belong to, and their readers refuse another character's.
- Quick fixes vs design work: small fixes, each a few lines: a page-start key used by the join and the re-target (wsClient.js:578-599); the heartbeat and joinTown stamp that key (BroTown.jsx:8853, 12142); the 'auth' mint refuses when the shared key differs from the key the join carried and reloads instead (wsClient.js:1477); applyAccountLogin and the mint use CHAR_CACHE_KEYS plus the session copies (index.js:229, wsClient.js:1495); an id stamp on `bt_resume` and `bt_rpg`. Design work: per-tab identity or one character per browser; the stash-merge trust; the list's active-key exemption from remote tombstones and a dedupe by player id across addresses (with N1-8).
