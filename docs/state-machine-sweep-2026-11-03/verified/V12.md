# V12 · Stored social relationships and their exits (parties, leaders, friends, blocks, the anti-bot record)
- Verdict: needs-thought
- Severity: high (player safety: a block made on the Friends page is silently erased by the next block or unblock on any player card, and a blocked friend can still message you; also a player stuck unable to send friend requests, the owner's bot flags erased on a busy day, and a former clan left with an absent leader forever)
- Who can trigger it: honest player (block a friend from the Friends page, then Block or Unblock anyone from a player card in the same session; or send 25 friend requests nobody answers); a busy day (128 different players joining since the room last restarted) for the bot record; nobody at all for the absent clan leader (already in the data); owner only (flipping `partykeep`) for the party roster bugs
- Summary: Players keep relationships: parties, friends, blocks, and a hidden anti-bot record. Your block list has two copies: the player card writes back the copy it read at load, silently erasing blocks made on the Friends page since. Blocked friends can still message you. Sent friend requests never expire and can't be cancelled, so 25 ignored ones stop every new request, and the error is never shown. A busy day can erase the owner's bot flags; a former clan whose leader never returned can never get a new one.
- Key files: src/ui/panels/InspectPlayerPanel.jsx:668, src/ui/BroTown.jsx:2099, src/networking/gameEvents.js:652, server/src/friends.js:123, server/src/botfp.js:293, server/src/party.js:592

## The machine
- Entity, and where its state lives:
  - a party and each player's membership: server memory `_parties`, `_partyByPlayer`, `_partyUnknownIds` (server/src/party.js:221-223), each party's `members`/`meta`/`leader`; storage `party:<id>` and `party_by_player:<pid>` (party.js:185-210); writers in party.js, clanparty.js:143-162, alliance.js (via `_partyStore`), persistence.js (a character restart calls party.js `_partyOnReset`, party.js:280-309); three live switches (`partykeep`, `alliance`, `clanparty`) change what a roster means;
  - a friendship between two players: storage `friends:<pid>` {list, reqIn, reqOut} (server/src/friends.js:55-75) and `friend_msg:<pid>` (the offline DM box); the phone's copy in the friends store (`doc`, `openThread`, `lastError`, src/ui/mobile/sheet/friendsSync.js:23-25), the DM archive `bt_dm:<fid>` and `bt_dm_unread`, the old device list `bt_friends`, and BroTown's React `friendsList` (src/ui/BroTown.jsx:2089-2098);
  - a block (this device only, never the server): localStorage `bt_blocked`, written by the Friends page (src/ui/mobile/sheet/friendsModel.js:149-155) and the player card (src/ui/panels/InspectPlayerPanel.jsx:655-671), read fresh by every chat lane and request filter (src/game/chatMute.js:67-75), and BroTown's React `blockedList`, read once at page load (src/ui/BroTown.jsx:2099-2108) and handed to the card;
  - one identity's anti-bot record: server memory `_botfp` Map, capped 128 (server/src/botfp.js:289-305), storage `botstat:<id>` (botfp.js:550-566).
- States:
  - partyless: in no party;
  - member online / member offline (kept, `partykeep` on) / member away (`partykeep` off, grace running);
  - unknown: the stored party could not be read, or is a newer shape (party.js:226, 241);
  - ghost member: listed by a party in memory while their own index names another, or none (reachable only after a switch flip);
  - leader present / leader absent with a `seen` stamp (handed on after 7 days) / leader absent with `seen` 0 (never handed on);
  - strangers / requested (A.reqOut[B] + B.reqIn[A]) / friends (both lists) / one-sided (one list, or one request half);
  - not blocked / blocked / blocked in storage but not in the card's copy (the card shows "Block", and its next write erases the block);
  - the phone's error slot: empty / holding (nothing ever empties it); a DM thread: closed / open (unread not counted);
  - anti-bot record: absent / hydrated (read at the join) / fresh (made without a read) / dirty / written / evicted.
- Moves:
  - accept an invite: partyless → member (party.js:423-494);
  - join with no party in memory, `partykeep` on: stored party loaded, members healed by their own index; a failed read → unknown (party.js:218-276, 568);
  - leave or kick: member → partyless; one left → disbanded (party.js:504-546);
  - disconnect: `awaySince` and `seen` stamped (party.js:550-558);
  - tick, `partykeep` off: away past 2 min → removed, only if `awaySince` is set (party.js:627-632) — members loaded while offline never have one;
  - `partykeep` flipped at runtime: no hook (server/src/liveops.js:318-345 reacts only to oneformula, movepath, monstermoves, off_*); writes stop (party.js:176) while the in-memory party keeps changing;
  - a member's join, leader offline, `seen > 0` and 7 days old: leader → first member online (party.js:588-596); `seen` 0 never moves;
  - clan conversion: a stored party, `seen: 0` for every member offline at that moment, the leader included (clanparty.js:145, 158);
  - friend_request: strangers → requested; crossing requests → friends (friends.js:114-150);
  - friend_accept / friend_decline / friend_remove (friends.js:154-207); no withdraw and no expiry: the router has only these five cases (server/src/index.js:5945-5959);
  - friend_dm: delivered, boxed, or dropped silently (friends.js:212-251); the sender's phone shows it as sent at once (src/ui/mobile/dash/SocialPanel.jsx:147-154);
  - friend_error: error slot empty → holding; `takeError()` has no caller (friendsSync.js:67-68);
  - Friends-page Block: reads `bt_blocked` fresh and appends (friendsModel.js:149-155); does not touch BroTown's copy or the server friendship;
  - player-card Block / Unblock: writes BroTown's load-time copy plus or minus one id (InspectPlayerPanel.jsx:655-671), erasing anything the Friends page added since;
  - anti-bot join: hydrate stored over live (botfp.js:228-287); any hit, strike, cook or start with no record → fresh record (botfp.js:289-305; server/src/botsig.js:230-235); 128 records → the 32 with the oldest `lastStrikeAt` (0 for anyone who never harvested, online or not) flushed and dropped (botfp.js:293-301); the close flushes and keeps (botfp.js:569-575).
- Diagram edges:
  - `Partyless --accept--> Member`
  - `Member --leave / kick / restart--> Partyless`
  - `Member(offline, loaded) --partykeep OFF: no awaySince--> Member(offline) forever !!`
  - `Member(away) --partykeep OFF sweep, then ON + rejoin--> Partyless, stored index dropped !!`
  - `LeaderAbsent(seen>0) --member joins after 7 days--> LeaderOnline`
  - `LeaderAbsent(seen 0, converted clan) --member joins--> LeaderAbsent(seen 0) !!`
  - `Strangers --friend_request--> Requested`
  - `Requested --accept--> Friends`
  - `Requested --decline--> Strangers`
  - `Requested --withdraw / expiry--> Strangers !! (missing)`
  - `Friends --remove--> Strangers`
  - `NotBlocked --Friends-page Block--> Blocked`
  - `Blocked --player-card Block/Unblock of anyone--> NotBlocked !!`
  - `BotRecordHydrated --eviction, then a hit or cook--> Fresh --first put--> stored flags erased !!`

## What needs further thought
- Should a block follow the player everywhere and cover everything: be kept by the server (as mutes already are), also stop DMs and friend requests, and should blocking a friend also unfriend them?
- Should a sent friend request run out (say after 30 days), and should the Sent list have a Cancel button? Should a refused request say why?
- For a former clan whose leader never came back: should the 7-day hand-on count from the day the clan became a party? And what should flipping `partykeep` do to parties already in memory?
- Making it explicit: one relationship store on the phone, like chatMute.js (one module that reads, writes and notifies), used by the Friends page and the player card, with BroTown's copies subscribing; better, a server-kept block list with `block`/`unblock` messages that the DM, request and chat lanes all ask. On the server, a friend request record `{at}` with a lazy expiry at the requester's join plus a `friend_cancel` case, both docs written in one run (no await between the two puts), and a refusal when either list is full. For parties, one transition function for a member (`online | offline | away | unknown`), a leader idle clock of `seen || at || ts`, and the switch flip as an explicit hand-over (off: drop stored parties from memory or stamp `awaySince` on every offline member; on: drop the in-memory parties so storage is read again). For the anti-bot record, never evict a record whose player is online (or re-read storage when one is recreated), and drop a record at the close after its flush.
- Quick fixes vs design work: one-line or few-line fixes: the card reads `bt_blocked` fresh before writing (or goes through friendsModel's helpers); `isBlockedId` on `friend_dm`, `friend_dm_backlog` and the Requests rows; a toast that consumes `friend_error`; `seen || at` as the leader's idle clock; an `includes` check before the accept's push; the anti-bot eviction skipping live sessions. Needs the owner's decision: a server-kept block and whether it unfriends; request expiry and a Cancel button; what the `partykeep` switch should do at runtime; whether a DM should show "not delivered" (it needs an answer from the worker).
