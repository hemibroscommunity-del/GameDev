# V13 · The kill switches before they load: a cold room ignores every thrown switch on its web requests
- Verdict: needs-thought
- Severity: medium (a player stuck: an honest player on a new device is refused at the login door, and the character list's restart is refused, while the owner believes the device lock is off. No items or gold are lost, and it fixes itself once anyone opens a game connection. The owner's overview also shows the switches as not thrown.)
- Who can trigger it: an honest player, only while the owner has thrown `devicelock: false` and nobody has opened a game connection since the worker last started (an empty room at a quiet hour after an idle eviction, or seconds after a deploy). Steps: on a new phone or computer, a cleared browser, a private window or the home-screen app, type an OLD-style Login Key at the login door, or restart a character from the list. New server-made keys skip the lock, so they are unaffected. The overview's wrong display needs the owner (admin key, e.g. the curl in OPERATIONS.md).
- Summary: The server keeps its kill switches in memory, but loads them only when a phone opens a game connection. The login door and the character list's restart are web requests that come first. In an empty room (a quiet hour, or just after a deploy), they read the device lock as ON even after the owner switched it off, so a player typing their key on a new device is still refused. The owner's overview shows the same wrong state. It fixes itself once anyone joins.
- Key files: server/src/index.js:4875, server/src/devicelock.js:126, server/src/account.js:180, server/src/liveops.js:115, server/src/admin.js:146, docs/specs/liveops.md:21

## The machine
- Entity, and where its state lives:
  - The room's live-flag cache, `this._liveFlags`.
    - Loaded only by `_liveFlagsEnsure` (liveops.js:115-118, the only writer in server/src) from storage `liveflags`, and changed in place by POST and DELETE /flags (liveops.js:336-337, 352-354).
    - Read synchronously by `_flagOn` and `_flagNum` (liveops.js:124-134), and by about 100 hand-written `const f = this._liveFlags` readers (e.g. devicelock.js:126-129, loginkeys.js:70-73, testmode.js:89-92, party.js:166-169).
  - A sub-machine on the same switch: the device lock's one-time fill.
    - Memory: `_devFilled`, `_devFillP`, `_devFillFailAt`, `_devFillInfo` (devicelock.js:165-173, 221-222).
    - Storage: `devlock:filled` (devicelock.js:220).
- States:
  - Unloaded (cold): nothing in memory. Every thrown switch reads as not thrown:
    - `_flagOn` is false;
    - an "on unless `x: false`" reader is ON;
    - `_flagNum` gives its default.
  - Loaded (warm): the stored switches are in memory, and every reader is right.
  - Written: memory changed in place, then the put is awaited (liveops.js:336-337). There is no gap in practice (see the REFUTED line).
  - Fill not run: no `devlock:filled`, and `_devFilled` is unset.
  - Fill running: the `_devFillP` promise (devicelock.js:168-172).
  - Fill failed: `_devFillFailAt`; it is tried again at most once a minute (devicelock.js:167).
  - Fill done: `devlock:filled` is stored and `_devFilled` is true (devicelock.js:180-181, 220-221).
- Moves:
  - Worker start (deploy, idle eviction, the first request of a quiet room): any → Unloaded. The constructor sets nothing (index.js:1020-1528), and the cache is never reset during a worker's life (liveops.js:117 is the only writer).
  - Socket upgrade on `/ws`: Unloaded → Loaded (index.js:4911). This is a storage read under the input gate. It runs before the room cap (4915), the per-address limits (4923), any session (4935) and the tick (4937).
  - GET, POST or DELETE `/api/admin/flags`: Unloaded → Loaded (liveops.js:317, 332, 351).
  - These run only for a session, so the cache is already Loaded (redundant): a join (join.js:1681), the capes (eventcapes.js:378), clan parties (clanparty.js:47-49).
  - POST or DELETE /flags: Loaded → Loaded, written through (liveops.js:336-337, 352-354).
  - MISSING load (they read switches while Unloaded and never load):
    - `/api/account` login and restart (index.js:4875-4877);
    - `/api/admin/*` other than /flags (index.js:4885-4887; the overview at admin.js:146-190);
    - `/api/market` (4863);
    - `/api/store` (4867);
    - `/api/arena` (4871);
    - `/api/botstat` (4880);
    - `/_room_count` (4856).
  - Routes that are safe while cold:
    - socket messages and closes: they need a session (index.js:4998-4999), and hibernated sockets are closed on wake (index.js:1520-1527);
    - every HTTP write: it needs a live session (httpauth.js:56-66);
    - `/api/arena`: its tournament is kept in memory only (gladiator.js:253, 318);
    - `/api/botstat` and `/_room_count`: they read no switch;
    - `/api/admin/grant` to an offline player: it goes to the mailbox and reads no switch.
  - Routes that are wrong while cold:
    - the account door and restart (the device lock);
    - the admin overview (display);
    - `/api/admin/dev/botflags` and `/dev/hidden` (`hidden_off`, display; S2-20's);
    - the first market or store read (the sword conversions).
  - Fill moves:
    - The first device decision for a character with no list: not run → running. Callers: the join (devicelock.js:229-232), the door (246-249) and the owner's tools (263, whatever the switch).
    - running → done (devicelock.js:220-222) or failed (167-171).
    - failed → running, 60 s later, at the next decision.
- Diagram edges:
  - `Asleep --worker starts (deploy, idle eviction)--> Unloaded`
  - `Unloaded --socket upgrade /ws (index.js:4911)--> Loaded`
  - `Unloaded --GET/POST/DELETE /api/admin/flags--> Loaded`
  - `Unloaded --login door or list restart (/api/account)--> Unloaded !! reads devicelock as ON`
  - `Unloaded --/api/admin/overview--> Unloaded !! reports thrown switches as on`
  - `Unloaded --first /api/market or /api/store read--> Unloaded !! conversions ignore swordconvert/gscopper`
  - `Loaded --POST/DELETE /flags--> Loaded (written through)`
  - `Loaded --deploy or idle eviction--> Unloaded`
  - `FillNotRun --first decision for a character with no list--> FillRunning`
  - `FillNotRun --cold door with devicelock:false--> FillRunning !! the switch says nothing is read or written`
  - `FillRunning --scan and writes done--> FillDone (devlock:filled)`
  - `FillRunning --throw--> FillFailed`
  - `FillFailed --60 s later, the next decision--> FillRunning`

## Concerns, verified
- [CONFIRMED] S2-6 / S2-17 (divergence): with `devicelock: false` on file, a cold room's login door answers `device: 'unknown'` and its list restart refuses `'device'`, while a join on that same worker is let in.
  - Evidence:
    - index.js:4875-4877, which runs before the warm-up at 4911;
    - devicelock.js:126-129, 243-252;
    - account.js:106, 180-181;
    - the client switches nothing on 'unknown' (AccountLoginForm.jsx:90-93), and opens no socket on the door (wsClient.js:311).
  - How checked: I ran the real `accountMethods`, `deviceLockMethods` and `liveopsMethods` on a fake storage (SM/round2/v13work/colddoor.mjs):
    - cold: 'unknown' and 'device', nothing wiped, `liveflags` never read;
    - after `_liveFlagsEnsure`: 'ok', and the restart runs.
    - The device-lock test sets the cache by hand (device-lock.test.mjs:66-69, 338), so nothing tests the cold door.
  - Docs:
    - device-lock.md "The switch" says "Nothing is read or written for this";
    - OPERATIONS.md:164-168 names this switch as the remedy when the lock "gets in honest players' way";
    - liveops.md:21-23 rests the fail-open on "every gated path requires a joined player", which the door is not.
- [CONFIRMED] S2-6 (the fill): in a cold room whose fill never ran, the door runs the one-time fill despite the switch. It lists every `device:` and `botstat:` record and writes `auth:` lists and `devlock:filled`.
  - Evidence: devicelock.js:246-249, 178-223.
  - How checked: colddoor.mjs case D (puts `auth:<id>` and `devlock:filled`, then refuses).
  - Docs: device-lock.md "The switch".
  - Impact is low: production has very likely filled already, since the lock shipped on and the marker stops it for ever (devicelock.js:180-181). It bites a fresh room.
- [CONFIRMED] S2-17 (stale design note): the join reads switches before its own load: join.js:523, 547 (device lock), 675 (account check), 856, 921 (`_loadRpg`); the load is at join.js:1681. This is right only because the socket upgrade loaded the cache first (index.js:4911). There is no live bug for joins: sessions exist only after 4911 (index.js:4935, 4998-4999).
  - Evidence: liveops.js:35-39 and 121-123 (the header and the comment), liveops.md:21-23.
  - How checked: traced every write of `_liveFlags` and every entry point (fetch, webSocketMessage and Close, tick start index.js:4937; no `alarm`).
  - Docs: the comment describes a guard that is not the real one.
- [CONFIRMED] S2-17 (overview): on a cold room, `/api/admin/overview` reports `deviceLock.on`, `loginKeys.on`, `testMode.allowed` and `lastPlace.on` as not thrown.
  - Evidence:
    - admin.js:146-190 never loads the flags;
    - devicelock.js:331-337, loginkeys.js:208-211, testmode.js:177-183, lastplace.js:235-238.
  - How checked: v13work/coldoverview.mjs, with switches stored → cold: all true; warm: all false.
  - Who sees it: it is display only, for the owner by curl (OPERATIONS.md:155-163). The in-game Test panel (ZoneHeader.jsx:111-115) normally has a socket, so it is warm.
  - Docs: none on it.
- [CONFIRMED] V13 (new, the same class; market and store): the first public market or auction-house read of a worker's life rebuilds the index. It rewrites stored orders and listings through the sword and greatsword conversions, reading `swordconvert: false` and `gscopper: false` as not thrown.
  - Evidence:
    - index.js:4863-4869, before 4911;
    - market.js:195, 115-118;
    - store.js:541, 448-455.
  - How checked: traced. The writes need a live session (httpauth.js:56-66), so only this rebuild runs cold.
  - Who can trigger it: a phone's Exchange poll between a deploy and its reconnect, or anyone calling the public GET.
  - Docs: swordconvert.js:110-114 and gscopper.js:149-153 promise the switch stops "the shelves' rebuilds".
  - Impact is low: the conversions are idempotent and very likely already applied.
- [CONFIRMED] V13 (new; party): the cold list restart reads `partykeep` as ON and edits the stored party rows (`party_by_player:`, `party:`, `ally:`) that `partykeep: false` says are untouched.
  - Evidence: persistence.js:542, party.js:166-169, 280-310.
  - How checked: traced, plus the coldoverview.mjs `_partyKeepOn` result.
  - Docs: party.js:164-165.
  - Impact is negligible: taking a restarted character out of its stored party is what the switched-on state would do anyway.
- [PLAUSIBLE] S2-6 (stall): the fill lists `device:` and `botstat:` whole, with no limit (devicelock.js:190, 196), inside the first decision that needs it, holding the room's input gate. A failed fill repeats the whole scan at the next decision a minute later (devicelock.js:166-171).
  - Unproven link: that a fill ever fails. It runs once a room and is marked done on success (devicelock.js:220).
  - Docs: handoff rule 9's second edge; device-lock.md "The devices the server already knew".
- [PLAUSIBLE] S2-6 (stuck): a known device is never refreshed (devicelock.js:237, by design for cost), and the 13th device drops the oldest one added (devicelock.js:154-156), even a daily phone. That phone is then refused until another pass.
  - Unproven link: a character with 12 listed devices. Past the first device, a new one comes in only on the owner's pass (devicelock.js:140-146), or as one of up to 12 from the fill (devicelock.js:213-214).
  - Docs: device-lock.md "Storage" says "the oldest added dropped past 12".
- [REFUTED] S2-17 (persistence): POST /flags changes memory, then puts (liveops.js:336-337), so a failed put would leave memory ahead of storage. What stops it:
  - the value is checked as small and storable before the put (liveops.js:322-334; 64 flags at most), so the put has no predictable failure;
  - a storage fault is the runtime's to handle. Cloudflare's output gate (what handoff rule 10 rests on) resets an object whose write fails, and that wipes the cache too. This runtime link is from Cloudflare's design and cannot be checked in this repo;
  - the owner sees the 500 at once (admin.js:457).

## What needs further thought
- Should every web request the room answers load the switches first? It costs one storage read per worker start, which the socket path already pays. The alternative is to keep a list of which web routes may read a switch.
- Fail-open was chosen because "only joined players reach gated code" (liveops.md:21-23). The account door, the admin overview and the market and store rebuilds now break that. Change the rule, or fix the routes?
- While `devicelock: false` is thrown, should the owner's device tools still run the one-time fill (devicelock.js:263)? And is "oldest added dropped past 12" right for a phone played every day?
- Making it explicit:
  - Give the cache one declared phase (unloaded or loaded) and one transition: `await this._liveFlagsEnsure()` at the very top of `GameRoom.fetch` (before index.js:4856), next to `_hiddenEnsure`. Every HTTP and socket route then runs Loaded.
  - Put the hand-written `const f = this._liveFlags` readers behind one accessor, `flag(name, dflt)`, that knows the phase and logs a read made while unloaded.
  - Add one suite check: send the real `fetch` for `/api/account/login` to a fresh room that has `liveflags` stored.
- Quick fixes vs design work:
  - One-line fixes: the warm-up at the top of `fetch`, or in `_accountFetch` and `_adminFetch`; correcting liveops.js:35-39 and 121-123 and liveops.md:21-23; adding a cold-room check to the `device-lock` suite.
  - Owner decisions: whether the fill scans everything in one go (rule 9), the 12-device drop rule, and whether the owner's tools should obey the switch.
