## What sitting 60's merge taught (part 11, 2026-11-24)
- BEFORE merging a list, grep every listed PR's body for a closing keyword before a PR's number (`(close|fix|resolve)[sd]? #N`): GitHub CLOSES #N when that PR merges ("which fixes #2300's red ..." closed #2300; reopened with `update_pull_request` state open, then merged).
- GitHub calls a PR whose head and main have TWO MERGE BASES "has merge conflicts" though the merge is clean here. Merge the others first if a local run of that order gives the rehearsal's tree; then, for each refused one, build `git merge --no-ff origin/main` on its head here, check that the merges give the rehearsal's tree, run precheck (the scratch worktree needs `npm ci` in the root and in `server/`; about 12 minutes a run), push it to the PR's branch, wait for `test` on the new head, and merge with that head. The top of a linear stack lands the PRs beneath it in one merge. Ask the gatekeeper to list such stacks as ONE line next time.
- A check's state costs little through `gh api repos/.../pulls/N --jq` (one line); `pull_request_read get` prints the whole body.
- The owner's messages each reprint the start-up brief (about 9,000 tokens): twenty of them is a part's whole memory. Answer shortly, and ask for the next part by 180,000.
