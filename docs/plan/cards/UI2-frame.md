## How it is built (finish.md part 5, rule 5)

- `src/game/dashNav.js`, no imports: ONE state (which workspace is up; each workspace's own stack; hidden or shown) and ONE transition function (open Gear, open Menu, go to a page, Back, Close, a shortcut's arrival, the Menu shortcut). A stack entry holds its page's id, its kept scroll and selection, `who` (whose page: none means yours; step 9 sets it) and `from` (where it grew from). `src/game/dashDests.js`: the destinations' table (id, word, picture, its place in the Menu, which workspace), which later steps add rows to.
- `tools/guards/dash-nav.test.mjs` (never `server/test/`: a file there deploys the worker): what it DOES. THE DODGES it must catch, each planted and seen red (name the plants in the PR body): Back goes to the category's parent instead of the page you came from; Close empties a stack; opening Gear clears the Menu's stack (or the reverse); a shortcut to the page already on top pushes it twice; the same page twice in one journey shares one scroll; resume lands on a page the worker no longer offers (a cap gone) instead of falling to the Menu's root; Back at the Menu's root does nothing instead of going to Gear; the Menu shortcut resumes instead of going to the root; opening the Menu from play goes to the root instead of resuming; after the Menu shortcut, Back from the root walks into the pages that were open before it; a page's `from` or `who` is lost when another page is pushed over it and popped.
- `dashboardPanelBus.js` becomes a thin face over `dashNav` (`open`, `push`, `pop`, `toBar`, `state` keep their meaning for every caller and the 44 tests). `BottomDashboard.jsx` gains calls and loses lines (say the count before and after).
