# The heap trim of 2026-11-13 (v2.3.5007)

The owner, 2026-11-13: "Go recommended" -- trim the page's JavaScript heap.
The memory check (`mp-membudget`, lines in `tools/qa/mp/memory-budget.mjs`)
read its `heap` line ("the page's JavaScript objects", 38.5 MB) at 36.5-38.0
MB on CI, on main as on every branch, so any pull request could fail it by
the luck of the run. This lane looked at what the heap holds at the check's
stops and trimmed what is kept with no use, without changing anything a
player sees or hears, and without raising the line.

## How it was looked at

`QA_MB_SNAP=0,5,6 QA_MB_SNAPDIR=<dir> node tools/qa/mp/run.mjs membudget`
writes a heap snapshot at those stops (0 arrival; 1, 3, 5 the three fights;
2, 4, 6 home after each). Builds: the real one (`npm run build`) and one
with names kept (`npx vite build --minify false --outDir dist-prof`, then
`mv src/dist-prof dist-prof`; run with `QA_DIST=dist-prof`). The snapshots
were read with a small script: size by kind, by the module variable that
holds each object, retained sizes, and the difference between two stops.

## What the heap holds (third fight, ~35-37 MB)

- **About half is compiled code** (~17.5 MB): the engine's machine code
  (~10 MB), bytecode (~2.4), its tables. It grows as more of the game runs
  (home after trip 1 -> after trip 3: +2.0 MB, of which +1.5 code). Chrome
  never threw any of it away here, with or without the check's DevTools
  connection (a test page's run-once function kept its bytecode 90 s and 20
  collections later), and a module's own top-level code is never thrown
  away. Not trimmable without running less code.
- **The rest is spread thin** (~17.5 MB): no holder over ~1.2 MB. The biggest
  were Pixi's frame textures (~5,500 Textures, ~2.9 MB with their Rectangles
  and boxed numbers: the looks' frames, the head pieces', the old body bakes),
  the look palette's frame records (~1.0 MB), the head-piece cache (~0.7 MB),
  Pixi's renderer state (~1.2 MB), the minimap (~0.6 MB), the live monster and
  figure displays, the shader sources (~0.5 MB, each kept 3-4 times by Pixi as
  cache keys), and Playwright's own injected script (~0.65 MB, test-only).
- **~260,000 boxed numbers (2.3 MB).** Chrome (with compressed pointers)
  keeps a number field that has ever held a fraction as a "double" field and
  boxes every value in it, whole numbers too: every Pixi Rectangle field
  (15,000 Rectangles), Matrix, point and Bounds.

## The trims (`?heaptrim=0` turns all four off: `src/rendering/heapTrim.js`)

1. **Head pieces' notes** (`entityRenderer.js` `_traitMetaLean`): each
   meta.json's `note`, `poseFitNote`, `poseNudgeNote`, `hoodNote` and
   `bboxes_source` (~170 KB of words over 66 pieces, read by nothing) are
   left out as it arrives; the rest is copied to a fresh object (not
   `delete`, which would leave it a slow dictionary read every frame).
2. **The look palette's frame records** (`lookPalette.js` `buildSheet`):
   made the first time a sheet's `frames` are read (its first draw), not for
   all ~190 sheets as they load, and every frame of a sheet shares its one
   whole-frame box (`orig`: the same numbers, never written).
3. **Pixi's batches' texture-id tables** (`batchIdsLean.js`): Pixi's
   `BatchTextureArray.clear()` set each id to null and kept the key, so each
   pooled batch kept every texture source id it ever drew, for the session
   (99 tables, ~0.35 MB at the fight, and growing with every Text made). The
   ids are removed instead, and a fresh table started every 512. Pixi reads
   an id only for a source it has just put in that batch; null and missing
   read the same.
4. **Whole numbers unboxed in Pixi's small geometry** (`fieldLean.js`): as
   the renderer loads, one throwaway Rectangle, Matrix, ObservablePoint and
   Bounds each get `null` in their number fields and their numbers back, so
   those fields are "tagged" for the class: a whole number then sits in the
   field, only a fraction is boxed. The same numbers, read the same way.
   Safari never boxes numbers, so there it does nothing.

## Readings

`mp-membudget` on this 4-vCPU box, main (`origin/main` at 0c9ef66, built
in a worktree) and the branch run back to back, one browser at a time; heap
in MB at each stop (arrival; then fight / home for each trip):

| run | arrival | t1 fight | t1 home | t2 fight | t2 home | t3 fight | t3 home | highest |
|---|---|---|---|---|---|---|---|---|
| main B | 32.3 | 35.1 | 35.6 | 36.7 | 36.7 | 37.5 | 37.6 | 37.6 |
| main D | 32.1 | 35.7 | 35.5 | 36.6 | 36.9 | 37.8 | 37.5 | 37.8 |
| branch A | 31.3 | 34.2 | 34.8 | 35.6 | 35.7 | 36.4 | 36.4 | 36.4 |
| branch C | 31.3 | 33.8 | 34.4 | 35.1 | 35.7 | 35.9 | 36.0 | 36.0 |

Earlier the same day: main 32.8 / 37.7 and 32.1 / 37.2 (arrival / highest),
the branch (three of the four trims) 31.1 / 36.1. So **about 1.0 MB less on
arrival and 1.3-1.6 MB less at the highest**, every other line the same, all
11 checks passing each run. CI's runner has read main ~0.5-1 MB above this
box, so the line of 38.5 should now have ~1.5-2 MB of room there instead of
~0.5.

The snapshots, the same stop (third fight), main against the branch (names
kept): 59,000 fewer boxed numbers (-0.70 MB), the notes' strings -0.19 MB,
Rectangles -0.15 MB, the batch tables 346 -> 108 KB; the rest is the
reading's own noise (how much code the fight compiled).

## Not done (proposals, for the owner)

- Pixi's shader cache keys (each shader's source kept 3-4 times, ~0.3 MB):
  would mean patching Pixi's program cache.
- The look palette makes a Texture for EVERY frame of a sheet the first time
  a look draws one of them (`lookFrames`); making them one at a time would
  save some of the ~0.6 MB of the looks' frames, at the cost of a check a
  frame. Not built: a change in a hot drawing path for a small saving.
- A Test-panel row for `heaptrim` (the house's way since v2.3.3755) would
  change `server/test/client-off.test.mjs`, and so deploy the worker on
  merge; left to the owner. `?heaptrim=0` turns it off for one phone.
