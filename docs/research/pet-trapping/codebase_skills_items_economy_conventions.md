### 8d. Cost of a new per-player storage record for a pet collection (e.g. `pets:<pid>`)
- WHY a key and not lifeSkills: today pets ride inside `lifeSkills` (saved whole, persistence.js:182) -- zero extra rows, but capped at 6, client-bootstrapped at first join (join.js:853), echoed to the client per key, and the ids are regenerated on every join (pets.js:90, :115). Rule 1 + the gear precedent say a growing collection gets its own key (handoff rule 2 table + precheck check 5).
- ROWS: Cloudflare DO paid pricing (docs/WORLD-ARCHITECTURE.md:293-301): rows written $1.00/M (50 M included/month), rows read $0.001/M, stored data $0.20/GB-month; today a player costs ~$0.001/hour of which saves are ~$0.0004 at ~340-450 rows/hour (:311-314); the free tier binds on 100k rows/day (handoff rule 4, :112-115). A separate pets key adds 1 READ per join (negligible) and 1 WRITE per pet-changing action (capture, release, rename, set active, hatch, feed). 100 pet writes/hour = +$0.0001/player-hour (+25% of the saves line). DANGER: pet XP per KILL written per kill would be the regen mistake again (rule 4: 5,455 -> 341 rows/h by coalescing) -- coalesce pet XP into the existing `_saveRpg` cadence or flush on interval/disconnect.
- ATOMICITY: an action that touches both bag and pets (capture consumes a trap; hatching consumes an egg) issues TWO puts; do them in one synchronous run with no await between (the farm branch's `_farmCommit`) and order them so a crash loses value rather than duplicating it (pet record first if it guards the replay, like the farm's bed; or persist-then-pay, guilds.js:51-57).
- SIZE: a gear_prov row (whole blob + id + slot + src + ts) is ~180-200 bytes, so 256 rows ~50 KB (gearprov.js:79-85); a pet is similar (~10 fields, pets.js:171-181). DO value limit 128 KB, key 2 KB (market.js:47-50). => cap the collection (e.g. 100-250 pets ~20-50 KB) with an honest overflow rule; 100k players x 10 KB = 1 GB = $0.20/month storage.
- JOIN PATH: one bounded GET per join is fine; never `storage.list()` a prefix on join (rule 9 second edge). Load before anything reads pets (gear_prov loads first, `_gearProvLoadOnJoin` join.js:699-708, for exactly this reason).
- LIFECYCLE CHORES the key brings: add it to `_resetCharacterData` (persistence.js:345-396 deletes `rpg:`, `oplog:questitem:<pid>:`, `gear_prov:` -- a pets key must be deleted there too or a restarted character keeps its pets); a shape version `v` like `FARM.V`/`GEAR_PROV_V` (gearprov.js:77) so a rollback never destroys newer data; the admin/snapshot surfaces (`rpgsnap:` snapshots only the rpg blob -- a separate key is NOT in the daily parachute, handoff table lines 82-84); the economy metrics walk only `rpg:` (liveops.js `_economyPage` prefix 'rpg:').
- Migration from today's `lifeSkills.pets` (6 max) into the new key needs a one-time adopt on join (the `gemsCaptured` stamp precedent, persistence.js:188-195) or a registry migration (`runRpgMigrations`, handoff rule 1).
