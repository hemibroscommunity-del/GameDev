## How this was run, and what it deliberately did not flag

The audit ran the repo's own `/repo-review` protocol (the seven
adversarial angles in `.claude/commands/repo-review.md`) across the whole
tree instead of a diff: 15 finders, each given `ARCHITECTURE-HANDOFF.md`
Part 1, `TRAPS.md` and `CLAUDE.md` as mandatory reading, then a skeptic
per slice whose only job was to disprove, then an independent confirmer
on the top tier. 90 candidates → 16 killed by skeptics → 74 survivors →
deduped to the list below.

Findings were rejected on sight for any of these, per the project's own
doc-trust rules:

- **"Code doesn't match the GDD / ARCHITECTURE.md"** — those are stale by
  owner directive (TRAPS #7). Code is truth.
- **Balance / progression tuning** — imbalance is policy (owner
  directive 2026-07-16). Level = 1 + T2 points placed.
- **The existence of client-side game logic**, of legacy `caps`
  fallbacks, or of v1-protocol paths — all deliberate (rules 19–21).
- **Anything already tracked** as SHIPPED or as an open backlog item in
  HANDOFF Part 2 — e.g. the EnchantPanel gem-slot consume (item A) is
  blocked for a documented reason and is not re-reported here.

Six candidates died specifically on TRAPS entries: two attempts to
re-derive party XP sharing (#3), one to server-roll the cook outcome
(#4), one to revive an `arena_bet` consumer (#1), and two GDD-restoration
proposals (#7).

## The headline: a large part of the shipped game has no way in

This is not a bug in any one file, and no test could have caught it. It
is the single most consequential thing in this report.

`src/ui/BroTown.jsx:3694` sets `S.nearBuilding = null` unconditionally,
every frame. The comment (v2.3.823) explains why and is honest about it:

> town building entrances removed (owner request). The town buildings
> have no in-game art yet, so their "Enter X" proximity prompts were
> floating over empty painted ground. … (Restore the BUILDINGS proximity
> scan here when building art ships.)

`enterBuilding()` (`src/game/interactions.js:34`) early-returns when
`nearBuilding` is null, and it is the **only** caller that ever sets
`buildingPanel` to a non-null value (`interactions.js:68`). The mobile
dashboard does not provide a second route: its six destinations are Bag,
Hero, Skills, Friends, Quests, More, and More contains only Journey,
Codex, Ranks, Clan, Guild, Settings.

So every one of these surfaces is currently unreachable by a player:

| Panel | System behind it |
|---|---|
| ExchangePanel | the marketplace order book (escrow, `mkt_order:`) |
| ForgePanel | amulet forge — smelt / craft / gem extract |
| GemcutPanel | server-settled gem cutting |
| EnchantPanel | gem slotting |
| WoodworkPanel / forge | weapon crafting |
| GamblePanel | gambling |
| BankPanel, VendorPanel, CookPanel, FarmPanel | banking, vendor, cooking, farm |
| PartyPanel | arena spectating + sponsorship UI |

The removal was intended as temporary and art-gated. What has happened
since is that roughly a year of server work settled *behind* those
panels — server amulet forge (v2.3.1192), gem cut (v2.3.1198), gem
extract (v2.3.1209), the order book fold into GameRoom (v2.3.1118) — and
none of it has a live entry point.

It also explains finding H-4 below: nobody noticed that `channelShim`
never forwards `amulet_forge_request`, because no player could open the
panel that sends it.

**RESOLVED 2026-08-03 — working as intended.** The owner confirms the
art does not exist yet, this is a pre-art demo, and the entrances return
with the art exactly as the v2.3.823 comment plans. No action. Recorded
here only so the next audit does not re-raise it, and because it is the
reason H-4 below went unnoticed: nobody could open the panel that sends
the dropped message.

## CRITICAL

### C-1 — `join` spreads the raw client blob into authoritative state
`server/src/join.js:155` · rule 16 · TRAPS #13 is the precedent

`_handleJoin` builds player state as `{ …defaults, ...msg.data }`. The
explicit ingest below it only re-assigns the `rpg*`-derived keys, so
**every other field the client sends survives verbatim** into
authoritative `playerState`. `session.data = msg.data` (`join.js:143`)
shares the same object, and `getAllPlayerData()` (`index.js:2996`)
spreads `...s.data` *last* — so forged fields also override real state in
the `state_sync` every joining player receives.

The worst instance: `_zoneEntryGraceUntil`. `_applyDamage`
(`combat.js:71`) — commented as "the ONE place player hp goes down" —
short-circuits to `dmgTaken: 0` while that stamp is in the future. A
join carrying `_zoneEntryGraceUntil: 4102444800000` is **permanent
immunity to every damage source in the game**: monsters, all PvP, duels,
arena matches, dungeon bosses. Their own offence is untouched.

No account is needed — `join.js:73` admits unregistered ids without a
passphrase, which is the deliberate legacy-client path (rule 21).

Consequences that move real value: a non-duel PvP kill spawns a pile
carrying the victim's entire inventory and then wipes it
(`index.js:1690`); wagered duels pay `wager × 2` out of storage escrow
(`duel.js:154`); the arena mints `CHAMPION_REWARD` 2000g
(`gladiator.js:463`) plus escrowed entries and sponsorship stakes;
`bounty:<pid>` pays the killer (`threat.js:207`).

I reproduced this against the real `GameRoom` under the repo's own mock-DO
harness: after a join carrying the field, `_applyDamage(ps, 9999, false)`
returns `{"dmgTaken":0,"graced":true}` with hp unchanged at 100.

The same spread also forges `ps.bro` — the Hemi Bro ownership badge that
`broverify.js` documents in three places as server-owned and unsettable,
and which is correctly kept out of `TRACK_COSMETIC_KEYS`.

**Fix:** do to `join` exactly what v2.3.1465 did to `track` — build a
sanitized copy from an **allowlist**, and filter `msg.data` itself before
`join.js:143` so `session.data` is clean too. Reuse
`TRACK_COSMETIC_KEYS` for the cosmetic half rather than writing a second
list that will drift. A denylist of today's known internals is a valid
same-PR hotfix but is not the fix — it reopens the moment anyone adds a
new `ps` field, which is precisely the failure mode TRAPS #13 records.

Note this falsifies the current wording of handoff rule 16 ("v2.3.1465 —
the surviving violation was `track`"). That line needs correcting in the
same PR (one line only — TRAPS #10).

### C-2 — T1 raw stats are persisted but never echoed: a new-device login zeroes the character
`server/src/persistence.js:238` · rules 1, 20

`power / vitality / endurance / agility / mind` are in `_saveRpg`'s fixed
field list (`persistence.js:102-106`) but **absent from the
`player_state` echo object** (`persistence.js:228-291`), and no other
channel carries them to the client.

The round trip that destroys them:

1. Player logs in on a new device (or via Login Key, or after clearing
   site data). Local `rpgState` has zeros.
2. Server loads the real values from storage (`join.js:444`) — correct so
   far. But it never sends them.
3. `BroTown.jsx:1955`'s effect fires on any `rpgState` change and emits
   `stats_update` carrying `rpgState.power || 0`, … — zeros.
4. `_handleStatsUpdate` (`grids.js:585-593`) accepts the client's number
   with only an **upper** clamp and assigns it. There is no floor and no
   "ignore a decrease" guard.
5. `_saveRpg` persists the zeros.

The character's five raw stats are permanently zeroed, server-side, by
the act of logging in somewhere new. This is the highest-value data-loss
bug in the report.

**Fix:** add the five to the echo's `full` object (old clients ignore
unknown keys, so it is deploy-order safe) and adopt them present-gated in
`wsClient.js`'s `player_state` handler beside `weaponSkills`/`hpSpec`.
Belt-and-braces: treat a reported T1 stat below the stored one as
advisory in `_handleStatsUpdate`.

### C-3 — a client-chosen zone id of `'__proto__'` kills monster AI for the whole room
`server/src/movement.js:21`, `server/src/index.js:443` · TRAPS #6

`_handleMove` writes `msg.z` straight to `ps.z` with no allowlist.
`this.monsters` / `this.nodes` / `this.loot` are plain `{}` keyed by that
string.

The sequence, verified line by line:

1. `move` with `z:'__proto__'`. A zone change always sets `accept = true`,
   so `ps.z = '__proto__'` is written (`movement.js:83`) **before**
   anything can fail.
2. `_ensureZoneMonsters('__proto__')` returns `Object.prototype` — truthy,
   so the `if (!this.monsters[zoneId])` guard never fires and no spawn
   happens.
3. That first message throws out of `_handleMove` and out of
   `webSocketMessage` (which has no try/catch around the switch). One
   socket dies. **But `ps.z` is now poisoned permanently.**
4. Every subsequent tick: `_activeZones()` includes `'__proto__'`;
   `_tickMonsters` gets `Object.prototype` back; `monsters.length` is
   `undefined` so the `=== 0` continue-guard does not fire; `for (const m
   of monsters)` throws *not iterable*.
5. `guard('monsters', …)` (v2.3.1562, `tick.js:71`) catches it — the tick
   survives, but **monster AI, respawn, monster→player damage and monster
   deltas are dead for all 60 players**, every tick, for as long as that
   one player's `ps.z` stays poisoned.

An unauthenticated attacker takes the shared room's combat offline with a
single message. The `guard()` that was added to stop one subsystem taking
down twelve is working exactly as designed here, and it is what turns a
crash into a silent, permanent outage.

**Fix:** validate the zone at the input edge, at **both** sources (`move`
and `join`) — one shared `_validZone(z)` accepting `town`, `farm_home`,
`worldview`, `hasOwnProperty.call(ZONES, z)`, or a `dungeon:` instance
this player is entitled to. The dungeon arm is required, not optional
(`dungeon.js:239` mints `'dungeon:' + id`). Converting the maps to
`Object.create(null)` is worth doing as defence-in-depth but is **not**
sufficient on its own — it fixes the prototype hazard while leaving
unbounded zone-key growth (L-19).

### C-4 — `forge_weapon` with `tierKey:'constructor'` mints free weapons
`server/src/gear.js:244` · rule 16 · TRAPS #6

`_handleForgeWeapon` validates the client's tier with
`const tier = table[tierKey]; if (!tier) return;`.
`BLACKSMITH_TIERS['constructor']` is a truthy inherited member, so `tier`
becomes the `Object` constructor function and **every downstream gate
compares against `undefined` and passes**:

- `skillLvl < tier.minLvl` → `5 < undefined` → false → passes
- `ps[reqStat] < (tier.statReq || 0)` → `< 0` → passes
- `(ps.coins || 0) < tier.goldCost` → `< undefined` → false → passes

Unlimited weapon mint, unlimited crafting XP, no resource cost. I
confirmed each comparison empirically.

This is the *same hole* handoff item H closed in `quests.js` and
`amulet.js:139` — the blacksmith/woodworker forge was missed in that
sweep.

**Fix:** `if (!Object.prototype.hasOwnProperty.call(table, tierKey))
return;` — the amulet.js precedent, verbatim.

### C-5 — prototype tier/type keys poison damage arithmetic with NaN
`server/src/gear.js:56` and `gear.js:138` · rule 16 · TRAPS #6

Two more instances of the same class, both load-bearing in combat:

`_weaponBase(type)` does `return T[type] || 6.25;`. The comment above it
justifies not validating `type` on the grounds that unknown types fall
back to the fists base — true for `'banana'`, **false** for
`'constructor'`, which returns a function. `(T['constructor'] || 6.25) *
2` is `NaN`. `_sanitizeWeapon` preserves `type` in both strict and
default modes, so the value reaches `_computeAttackDamage`, the
`_maxWeaponDmg` cap and `_weaponSellValue`.

`_sanitizeAmulet` gates on `if (!AMULET_TIER_POWER[a.tier]) return null;`
— and the comment directly above it *promises* that an unknown tier drops
the whole amulet so it "can't ride the `|| 1.0` fallback". A prototype
key is truthy, so the amulet is kept and rides into the authoritative
damage roll.

NaN damage propagates into shared monster HP, which is how this becomes
everyone's problem rather than just the cheater's.

**Fix:** `hasOwnProperty.call` guards at both sites, plus `index.js:1329`
`_wpnCat` which has the identical `C[type] || 'sword'` shape.

### C-6 — the 500 px/s anti-teleport cap is bypassed by flipping zone and back
`server/src/movement.js:55` · rule 16

The delta check is skipped entirely whenever `msg.z !== ps.z`
(`movement.js:52`, `const zoneChanged = newZone !== oldZone`), because a
legitimate zone change does move the player to a new spawn point. But
nothing validates the zone value and nothing rate-limits the flip, so
**two `move` messages — one to any other zone at the target coordinates,
one straight back — write an arbitrary position into the original zone.**

That defeats the range checks in `_handleLootPickup`, `_handleNodeStrike`,
`_resolvePvPAttack` and monster aggro distance — all of which compare
against `ps.x/y` after the overwrite. Those are the exact bypasses the
cap was written to close.

Worth noting: TRAPS #13 cites this cap as *the control that held* while
`track` was open. It does not hold.

**Fix:** validate the destination zone before writing `ps.z` (shares the
C-3 helper), and apply the speed check across a zone change too, using
the destination zone's spawn point as the reference position rather than
skipping validation altogether.

## HIGH

### H-1 — `monster_damage` has no attacker-zone, proximity, or alive gate
`server/src/combat.js:384`

`_handleMonsterDamage` resolves the monster from the **client-supplied**
zone and applies server-rolled damage without checking that the attacker
is in that zone, near the monster, or alive. Every sibling handler has
those gates (`gathering.js:316`, `index.js:2199`). A player can kill
monsters across zones from town, and reach into other players' dungeon
instances. Confirmed by execution against the unmodified tree.

**Fix:** add the sibling gate immediately after `attackerPs` resolves and
before the cadence lane.

### H-2 — the marketplace never checks the escrowed weapon against the listing
`server/src/market.js:183` · rule 16

`_mktPlaceOrder` takes `category`, `subtype`, `tierKey`, `element1`,
`element2` verbatim from the request and uses them to pick the order-book
bucket, while correctly escrowing the item from the server's own
`ps.weaponStash[idx]`. **Nothing cross-checks the two.** A seller can
advertise a worthless weapon into a high-tier bucket and match any
resting bid there at the bid's price.

This is a partial application of rule 16: the item is taken from server
state (right), but its *description* is trusted from the wire (wrong).

**Fix:** derive the index key from the escrowed weapon, not the request
body.

### H-3 — a "protected" duel/arena kill still destroys the whole inventory
`server/src/index.js:1746`

`_handlePlayerDeath` deliberately skips both the death pile and the
inventory wipe on a clean duel kill (`index.js:1689`). But
`_tickPlayerRespawn` (`index.js:1742`) wipes `ps.inventory`
unconditionally on every respawn and saves it. Because no pile was
spawned, the items are **destroyed rather than transferred** — five
seconds after the death that was supposed to protect them.

**Fix:** stamp `ps._noDropDeath` in `_handlePlayerDeath` and gate the
respawn-tick wipe on it, clearing it in the same block so normal deaths
still get the defence-in-depth re-wipe.

### H-4 — `channelShim` silently drops the entire amulet + gem economy
`src/networking/wsClient.js:1886`

`channelShim.send()` is a closed allowlist of 18 raw `type:` values plus
`{type:'broadcast'}`, with **no fall-through**. Any other typed message
is discarded before it reaches the socket.

Dropped today: `amulet_forge_request` (5 call sites in ForgePanel),
`gem_cut_request` (GemcutPanel), and `extraction_start` — the last of
which means the v2.3.229 gather-timing anticheat has been receiving
nothing in production since it shipped.

The client's local prediction still runs, so the UI shows success; the
server state never changes, so there is no v2 delta to correct it.
Currently masked by the building panels being unreachable — it becomes
player-visible the moment they are restored.

**Fix:** add the two passthroughs, then close the class — make the
trailing `broadcast` check an `if/else` so any unrecognised typed message
is forwarded by default rather than silently dropped.

### H-5 — `admin /kick` and `/freeze` skip the entire disconnect cleanup
`server/src/admin.js:189`

Both delete the session from the map *before* closing the socket, and
`webSocketClose` opens with `const session = this.sessions.get(ws); if
(session?.id)`. The entry is already gone, so the whole cleanup block
never runs: `playerState[pid]` is orphaned with `disconnected` unset,
duel/party/trade teardown never fires.

**Fix:** factor the `webSocketClose` body into `_teardownSession(ws,
session)` and call it from both admin sites before the delete.

### H-6 — the default-branch rebroadcast has no size or rate limit
`server/src/index.js:2922`

The router's default branch pushes the client's message verbatim into
`eventBuffer`, which the tick fans out to every socket. Nothing bounds
inbound frame size, per-client rate, or buffer length — only the per-tick
drain is capped. One client turns a 1 MB frame into ~60 MB of egress.

**Fix:** two gates at the top of `webSocketMessage`, on the raw frame so
they cover validated cases too: reject frames over ~8 KB, and a
per-session token bucket.

### H-7 — reconnecting mid-arena-match restores healing for one fighter
`server/src/gladiator.js:260`

`ps._arenaMatch` is the sole gate on town HP regen, hub stamina/mana
top-off, `eat_request`, shop healFish and the cook heal buff. It lives
only on in-memory `playerState`, which `webSocketClose` deletes, and
nothing on the join path restores it — while the duel itself survives via
`_duelOnDisconnect`/`_duelOnRejoin`. The match continues with the healing
gate lifted for one side only.

**Fix:** stop keeping the rule in a memory-only flag — have the five read
sites ask `this._duelFor(pid)?.arenaMatch`, which already survives the
disconnect.

### H-8 — join ids are unconstrained, so storage prefixes are not player-isolated
`server/src/admin.js:83` · rule 2

`msg.id` is client-chosen and validated only against the three magic
prototype names (`join.js:83`). Nothing constrains its characters or
length. `_rpgSnapshotMaybe` prunes with `list({prefix: 'rpgsnap:' +
playerId + ':'})`, so **an id beginning `<victimId>:` places its
snapshots inside the victim's prefix namespace**, where the victim's own
prune counts and deletes them by lexical order — destroying the rollback
parachute.

**Fix:** a positive charset/length gate at the join edge —
`/^[A-Za-z0-9_-]{1,64}$/` — which subsumes the prototype-name check and
closes the whole class of prefix-injection at one line.

### H-9 — unauthenticated join loops mint unbounded permanent storage
`server/src/join.js:405`, `server/src/index.js:2431`, `server/src/feedback.js:103`

Three related exposures on the unauthenticated surface:

- Every unregistered id persists a permanent `rpg:<id>` blob
  (`join.js:405`), a `device:<devId>` (`botfp.js:167`) and a Leaderboard
  row (`index.js:2964`). Nothing prunes any of them and there is no
  per-IP or per-connection join budget.
- `case 'join'` has no already-joined guard, so one socket can re-join
  unlimited times; `webSocketClose` deletes only the last id and every
  earlier `playerState` entry leaks for the DO's lifetime.
- `POST /api/feedback/submit` is public with no auth, its only throttle
  is `rate:<playerId>` **read from the request body**, `ticket:` keys have
  no cap and no delete path, and `playerName`/`topic` are stored
  unclamped and re-served.

**Fix:** per-socket join budget + per-IP window (the `account.js`
`_acctIp` map is the in-repo precedent); reject a join on a session that
already carries an id; clamp every feedback field before it reaches a
storage key and put tickets on a fixed-size ring, matching what
`crashReport` already does in the same file.

## LOW — selected

The full 50-item low tier is in the run journal. The ones worth knowing:

- **`preloadAnimations.js:60` / `wsClient.js:1145`** — `preloadZoneAssets`
  loads monster variants, the snowman and slime recolours per zone, and
  **nothing ever frees them**; only the map is freed. Dying in a zone
  frees nothing at all. This is the iPhone RAM problem the zone-asset
  exception was introduced to solve, partially re-accumulating.
- **`preloadAnimations.js:95`** — Frost's ice-burst impact sheet is kicked
  *unawaited* by the zone gate, so the first snowman impacts render
  nothing (TRAPS #12).
- **`entityRenderer.js:2116`** — hair-clip masks load on first sighting;
  only the local player's current hat is preloaded (TRAPS #12).
- **`wire-audit.test.mjs:55`** — the conformance extractors are
  single-quote/lowercase-only, and their rot floors now sit 30–50% under
  the live population. These tests mechanically enforce hard rules 13, 5
  and 19; a gap in an extractor is a gap in a rule.
- **`precheck.mjs`** — the whole-tree sweep covers 17 of 42 server
  modules, so handoff item H's "the sweep is now quiet" is narrower than
  it reads. C-4 and C-5 are in the uncovered set.
- **`optimize-assets.yml:10`** — never fires on new sprite art, so 57
  player/gear sheets 404 on `.webp` before every cold load.
- **`GameApp.jsx:591`** — no React error boundary anywhere: a render throw
  unmounts the root *and* kills the game's own black-screen recovery.
- **`cooking.js:229`, `dungeon.js:191`** — two more prototype-key holes of
  the C-4/C-5 class: `shop_purchase` with a prototype `itemId` zeroes the
  buyer's persisted gold; a dungeon `archetype` prototype key spawns
